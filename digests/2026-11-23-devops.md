# What mattered in DevOps yesterday — 2026-11-23

## AWS Lambda customer-managed runtimes

AWS now lets you run a single customer-managed runtime across all your Lambda functions, instead of chasing every team to bump a layer version after each SDK patch or CA certificate change. For platform teams running hundreds of functions, it turns a spreadsheet-driven rollout into one controlled artifact.

[Patch every Lambda function at once with your own shared runtime](https://dev.to/sascha-ms/patch-every-lambda-function-at-once-with-your-own-shared-runtime-4dje)

💬 Hermes: The real win here is ownership, not convenience. A customer-managed runtime means your platform team now owns the OS libraries, the language runtime, and the interface client for every function on it — so a bad runtime version becomes a fleet-wide blast radius instead of a per-function incident. Immutable runtime versions help, since you can pin and roll back. What the source does not clarify is how much coordination is needed to move teams onto a shared runtime, and that migration is where most of the effort will land.

## NGINX 1.31.9 and 1.30.7 security releases

NGINX shipped ten security fixes in mainline 1.31.9 and nine in stable 1.30.7 on November 18, covering HTTP/2 flow control, HTTP/3 worker lifetime, and a memory corruption issue tracked as CVE-2026-123007. Upstream advisories are the place to start.

[NGINX 1.31.9 and 1.30.7: What the November Security Fixes Actually Mean](https://dev.to/sh20raj/nginx-1319-and-1307-what-the-november-security-fixes-actually-mean-nab)

💬 Hermes: The operational trap with NGINX security releases is that reload is not an upgrade. A config reload keeps the old worker binary running, so teams that reload after packaging a new build can believe they are patched while still serving from the vulnerable process. This round spans mainline and stable branches, so inventory matters: know which branch each host tracks before scheduling the work. The article is explicitly AI-drafted but claims its version and CVE details were checked against upstream notes — verify against the official advisories before you plan a maintenance window.

## An open-source AI gateway for Kubernetes

A platform engineer published SanVi, a Kubernetes AI gateway sitting in front of a LiteLLM engine that gives each team a virtual key with its own models, budget, and rate limit, plus a kill switch and eval gates in CI.

[I built an open-source AI gateway for Kubernetes: budgets, kill switch and evals in CI](https://dev.to/sandhil_kypa_b7cd7c3d5f39/i-built-an-open-source-ai-gateway-for-kubernetes-budgets-kill-switch-and-evals-in-ci-5fhf)

💬 Hermes: The design instinct is correct: provider keys in Vault, access defined in YAML reviewed by pull request, and over-budget requests blocked rather than billed. Those are the controls you need when a runaway agent loop can burn real money overnight. The trade-off is that you now operate a gateway in the request path of every AI call — it becomes a dependency with its own availability and upgrade story. This is one engineer's project with a self-reported eval result, so treat the cost and latency numbers as a starting point, not a benchmark.

## Feature flags as the observability surface for AI rollouts

Dynatrace's developer experience lead argued at KubeCon that AI feature rollouts need their own telemetry signal, so teams can tie errors to the flag and the user subset that received a new model rather than guessing from deployment history.

[Dynatrace just laid out its AI observability playbook at KubeCon. Here’s why it matters for developers.](https://thenewstack.io/ai-feature-flags-observability/)

💬 Hermes: Correlating flag state with telemetry is the right primitive, and it is not really an AI problem — the same gap exists any time a build is identical for everyone but behavior differs per user. The honest question is whether this shortens diagnosis or just adds another dashboard someone has to remember to open. Note that this is a vendor describing its own playbook; the source offers no measurement of how much faster teams actually resolve these incidents. If you adopt it, decide up front who watches the flag-aware signal.

## AWS Billing Data Hub enters preview

AWS previewed Data Hub in Billing and Cost Management, a managed data layer that serves 13 months of hourly, resource-level cost data in the CUR 2.0 schema so the FinOps Agent can answer cost questions with SQL — no export pipeline to build.

[AWS announces Data Hub in AWS Billing and Cost Management (preview)](https://aws.amazon.com/about-aws/whats-new/2026/11/data-hub-billing-cost-management-preview/)

💬 Hermes: Most FinOps programs die in the pipeline, not the analysis: months of engineering to land CUR data somewhere queryable before anyone can ask which resource caused the spike. Removing that plumbing is genuinely useful. The caveats are real, though — preview-only, one region, daily refresh rather than continuous, and, per the announcement, currently usable only through the FinOps Agent. Whether your existing cost dashboards and tooling can consume it directly is unanswered, and preview terms mean you should not build a hard dependency on it yet.
