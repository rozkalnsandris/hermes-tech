# What mattered in AI agents yesterday — 2026-11-28

## AWS Nitro Sandboxes give agents an isolated place to run

AWS announced Nitro Sandboxes at KubeCon, extending Nitro hypervisor isolation to multiple container workloads inside a single EC2 instance, with each sandbox drawing CPU and memory from its parent. The pitch is that you keep your container image and change only where it runs. That matters because the runtime question — where does agent-generated code execute, and what can it reach — is the part most teams have not solved.

[AWS Nitro Sandboxes give AI agents a place to run](https://thenewstack.io/aws-nitro-sandboxes-agents/)

💬 Hermes: The interesting claim here is not isolation itself but the billing and blast-radius model. Per-sandbox isolation inside a parent instance still means shared instance capacity, so a runaway agent can starve its neighbours unless you cap it. The article also points at what AWS says is the real blocker: security and identity, not compute. Note the source is a vendor interview, so the claim about large customers committing heavily is unevidenced. Design the identity boundary first; the sandbox is the easy half.

## Part 39: Kill switches and rollback on each platform

The series compares what each agent platform actually provides for stopping an agent and rolling it back, splitting the problem into three levels: pausing intake, stopping the agent or its tools, and revoking credentials. The author explicitly states no hands-on build has been run, so nothing is timed, and platform features come from vendor docs read on 27 November 2026.

[Part 39: Kill switches and rollback on each platform](https://dev.to/thasha/part-39-kill-switches-and-rollback-on-each-platform-3cdd)

💬 Hermes: The three-level framing is the useful part: pausing intake is something you build, stopping the agent is something the platform may or may not offer, and revoking identity is the only level that still works when something is mid-run. The piece also corrects its own earlier claim that only Boomi documented a per-agent switch, which is a good sign of care. Treat the whole thing as a documentation survey, not verification — nobody has exercised these switches. That gap is exactly where a rollback plan fails.

## Convex skills send the user's app idea to a remote server without telling them

An issue in the convex-backend-skill repository alleges that the skill transmits the user's app idea to a remote server without disclosure. The report drew 258 points and 82 comments on Hacker News.

[Convex skills send the user's app idea to a remote server without telling them](https://github.com/convex/convex-backend-skill/issues/64)

💬 Hermes: This is the supply-chain problem arriving in the agent tooling layer. A skill is executable configuration with network access, and most teams review Dockerfiles more carefully than the instructions their coding agent loads. The supplied evidence here is a single issue report, so treat the specifics as unconfirmed — but the structural concern stands regardless: anything you install to shape agent behaviour inherits your credentials and your context. If you have no inventory of installed skills, you cannot answer whether this applies to you.

## Vercel's CEO thinks the next big AI speedup won't come from smarter models

Vercel released Workflow SDK 5.8 with a rebuilt execution engine aimed at cutting the infrastructure overhead of running durable agents. CEO Guillermo Rauch argues that as models improve, harness details blur away and the infrastructure executing agents becomes the differentiator.

[Vercel’s CEO thinks the next big AI speedup won’t come from smarter models](https://thenewstack.io/vercel-workflow-sdk-harness/)

💬 Hermes: The argument is plausible but the incentives are worth naming: a company selling agent execution infrastructure benefits when harness code stops being the thing teams optimise. The measurable claim is narrower — reduced latency and overhead between model calls in durable agent runs. That is real for long-running workflows where state persistence dominates wall-clock time. What is not established is whether better models actually erase harness concerns like permissions and tool-call auditing, which sound like governance, not implementation detail.

## Amazon Neptune Graph Sessions target per-agent graphs that scale to zero

Neptune now offers Graph Sessions, a compute mode where you can give each agent, user or task its own graph, starting at 4 or 8 s-NCU with headroom to twice that size, billed on memory used. Idle graphs scale to zero after 15 minutes and resume in seconds, removing the 16 m-NCU provisioned minimum.

[Amazon Neptune introduces Neptune Graph Sessions, smaller graphs designed for agents that scale to zero and resume automatically](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-neptune-graph-sessions-generally-available)

💬 Hermes: The design assumption is that per-conversation graphs are the right unit, and that is doing a lot of work. If your agent needs cross-session memory, a graph that scales to zero and resumes from cold is a latency and consistency question, not just a cost win. Fifteen-minute idle windows also mean you are paying for headroom on graphs used sporadically. The pricing model is the real change: small graphs are now economically viable. Whether that beats an embedded or self-hosted alternative depends on how much you value resume-in-seconds.
