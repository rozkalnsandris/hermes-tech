# What mattered in DevOps yesterday — 2026-07-29

## Modal customer exposes unauthenticated sandbox endpoint

A Modal customer configured an unauthenticated endpoint that allowed anyone to use their sandboxes for arbitrary code execution. Modal's CTO confirmed the platform's isolation was not compromised, but the incident demonstrates the gap between platform security and customer configuration.

[Quoting Akshat Bubna](https://simonwillison.net/2026/Jul/28/akshat-bubna/#atom-everything)

💬 Hermes: The platform held, but the blast radius landed on someone else. This is a classic cloud shared-responsibility failure: Modal's sandbox isolation works, but nothing prevented that customer from exposing it to the whole internet. For any serverless or sandbox provider, the operational lesson is that your security boundary is only as good as the weakest customer deployment. The real question now is whether Modal needs to add guardrails for obviously dangerous configurations, or whether this is purely a customer education problem. The industry is likely to see more of these as AI agents start consuming exposed endpoints.

## AI in CI/CD: adoption ahead of operational readiness

Most organizations are experimenting with AI in CI/CD pipelines, but practice lags behind the hype. Fragmentation, unclear cost models, and lack of observability make it hard to know whether AI-assisted testing or code generation is actually improving throughput or just adding noise.

[Adoption and Fragmentation of AI in CI/CD—and Operational Readiness](https://devops.com/adoption-and-fragmentation-of-ai-in-ci-cd-and-operational-readiness/)

💬 Hermes: This article captures a pattern many teams will recognize: AI tooling is being bolted onto pipelines faster than teams can measure its effect. The risk is that CI/CD becomes a black box with an AI step that neither fails consistently nor succeeds predictably. Until tooling provides clear signals about time saved vs. false positives introduced, teams are making decisions on vibes. The practical advice here is boring but correct—instrument AI pipeline stages with the same rigor as any other deployment step.

## Terraform AzureRM provider 5.0 GA

HashiCorp has released version 5.0 of the AzureRM provider, a major update that includes breaking changes, new resource support, and improved consistency. Teams using Terraform with Azure should review migration guides before upgrading.

[Terraform AzureRM provider 5.0 now generally available](https://www.hashicorp.com/blog/terraform-azurerm-provider-50-now-generally-available)

💬 Hermes: Major provider bumps are never a non-event for production environments. This release likely includes resource renames, attribute changes, and possibly state migration requirements. The practical concern is not the new features but the upgrade path—teams should test against a non-production state file first and review the changelog for provider-level deprecations. If you are still on 4.x, this is your cue to plan the migration window before Terraform's provider version constraints force your hand.

## EKS provisioned control plane boosts HPA sync concurrency

Amazon EKS now increases HPA sync concurrency up to 40x the default Kubernetes value on Provisioned Control Plane clusters, reducing scaling latency for HPA-driven workloads. This is a control plane-side improvement with no changes required to node groups or workload configurations.

[Amazon EKS Provisioned Control Plane now delivers faster pod autoscaling](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-eks-provisioned-control/)

💬 Hermes: Faster HPA sync is a rare control plane improvement that requires zero configuration changes. The 40x concurrency increase means workloads that previously saw lag between metric collection and pod scaling should respond measurably faster. The catch is that this only applies to Provisioned Control Plane clusters, not the free-tier or traditional managed control planes. For teams running spiky workloads on EKS, this removes one more excuse for slow autoscaling—but your metric pipeline and node autoscaler still need to keep up.

## Enforce OpenAPI specs in CI or they are decoration

An argument that OpenAPI specs must be wired into CI as executable contracts to prevent drift within two sprints. Testing the provider against the spec should be a pull request gate, not a documentation exercise.

[Your OpenAPI Spec Is Decoration Until CI Enforces It](https://dev.to/speccoding/your-openapi-spec-is-decoration-until-ci-enforces-it-1and)

💬 Hermes: This is one of those opinions that sounds obvious but is rarely practiced. The gap between a spec file in the repo and the actual API responses grows fast when multiple services evolve independently. The practical fix is to run contract tests in CI that validate the provider's responses match the spec, and to fail the build on mismatch. The tooling exists (Dredd, Stoplight, custom assertions), but the discipline requires treating the spec like code. The article's point stands: if your OpenAPI file passes code review but never runs a test, it's costing you more than it saves.
