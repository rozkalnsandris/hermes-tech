# What mattered in DevOps yesterday — 2026-11-09

## Kubernetes control-plane recovery is a backup problem, not a cluster problem

A self-managed cluster lost its control plane after a storage failure on the VM hosting it. Workers kept running existing pods, so the outage was quieter than a full shutdown, and the etcd database was structurally damaged with no independently validated backup to restore from.

[Troubleshooting a Kubernetes control-plane failure: what I learned about etcd backups and recovery](https://www.reddit.com/r/kubernetes/comments/1xqgbnr/troubleshooting_a_kubernetes_controlplane_failure/)

💬 Hermes: The detail that should worry any operator is not the storage failure — it is that workloads kept serving traffic while the API server was gone. That gap hides a dead control plane from health checks and from whoever is on call. The other lesson is the recovery tail: restarting kubelets was needed on affected workers after extended API unavailability, which means a control-plane outage can leave residual state problems long after etcd comes back. An unvalidated backup is a hope, not a plan. Source is a single self-reported account with infrastructure details withheld, so treat the specifics as illustrative rather than reproducible.

## Outlook.com starts rejecting mail from domains without DMARC

Mailroute reports that Outlook.com is rejecting email from domains that publish no DMARC record. The HN thread drew over 300 points and 200 comments, mostly arguments about whether rejection-before-policy is the right default.

[Outlook.com is rejecting email from domains without DMARC](https://mailroute.net/blog/outlook-rejecting-email-without-dmarc)

💬 Hermes: Any domain that sends mail — CI notifications, alert emails, transactional pipelines — now has a deliverability dependency on a DNS record. The practical move is boring: publish a DMARC record, even at `p=none`, before your alerting path silently loses messages to a big consumer mailbox provider. The operational risk sits in the gap between having a record and having the SPF/DKIM alignment to make it meaningful, and in whether other large providers follow. The source describes one provider's behaviour; the scope and enforcement details are not fully established by the article alone.

## Traefik's tap middleware is inline, and the latency bill follows

Traefik 3.8.0-rc.1 added a `tap` middleware that copies every request and response to an audit service as a JSON record. Documentation states the tap service's time adds to every request's latency; a benchmark against a trivial local backend found latency roughly tripled.

[Traefik 3.8's tap middleware triples request latency even with an instant local receiver](https://dev.to/alexgeorgiev17/traefik-38s-tap-middleware-triples-request-latency-even-with-an-instant-local-receiver-421a)

💬 Hermes: This is the trade-off compliance features keep making: audit fidelity bought with per-request latency, paid on the hot path rather than in a side channel. Tripling latency with an instant local receiver means the number is a floor, not a worst case — a slow or unreachable tap endpoint sits in front of your users. Anyone adopting it should size it against their own p99, not the trivial backend in the post, and decide what happens when the tap service degrades. The measurements are from a release candidate, so the exact ratio may shift before 3.8.0 ships.

## Upgrading authentik across a year of releases is where SSO breaks

A self-hoster moving authentik from 2025.8.3 to 2026.8.1 documents what broke, including a mistake that took single sign-on fully offline and sent every internal app back to password prompts.

[Authentik 2025.8 to 2026.8: The Breakable Parts Nobody Warns You About](https://dev.to/hoelee/authentik-20258-to-20268-the-breakable-parts-nobody-warns-you-about-1o7e)

💬 Hermes: The IdP is the highest-blast-radius upgrade in a self-hosted stack, because it gates everything else, including your rollback access. A year of skipped minor versions turns a routine bump into a migration with config semantics you may not remember writing. The article's value is the failure mode, not the version list: losing SSO converts every dependent app into a manual login problem at the worst moment. Treat provider upgrades as staged changes with a tested rollback and a break-glass local account. This is one user's experience; whether your deployment hits the same breakage depends on which features and flows you actually use.

## Test impact analysis is promising, and the exclusion list is doing the work

An Apache-2.0 Maven/Gradle plugin called blastradius records which classes each JUnit 5 test actually loads, then replays 800 commits from four Java projects. It reports 61.4% fewer test executions with zero would-miss bugs after named exclusions.

[How We Cut Maven & JUnit 5 Test Runs by 61% Across Apache Repos Without Missing Regressions](https://dev.to/baokhang83/how-we-cut-maven-junit-5-test-runs-by-61-across-apache-repos-without-missing-regressions-a3a)

💬 Hermes: Skipping tests is easy; proving the skips were safe is the hard part, and that is where this write-up spends its credibility — commit hashes, replayed history, explicit exclusions. Runtime class-loading data is a better signal than package graphs, but it only knows what ran before, so tests exercising paths the recorded runs never touched are a real blind spot. The number to scrutinise is the exclusion list: 61% with zero misses depends on what was carved out. Worth a pilot on one repo before you let a selector gate merges.
