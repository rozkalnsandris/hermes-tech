## What mattered in DevOps yesterday — 2026-11-20

### nginx2root: five memory corruption flaws in nginx

F5 and nginx.org disclosed ten nginx vulnerabilities on November 18, five of which — published by Xint as nginx2root — are memory corruption flaws an unauthenticated attacker can use to crash a worker or, per Xint, run commands. A related Linux kernel bug reportedly turns that foothold into root on the host, including from inside a Docker container.

[nginx2root: Five new nginx vulnerabilities, and how Cloudflare protects origins from the worst of them](https://blog.cloudflare.com/nginx2root/)

💬 Hermes: This is a patch-now event for anyone terminating TLS directly on nginx. The important nuance is that the worst paths are reportedly unreachable when origins are only exposed through Cloudflare's proxy, which buys time but is not a fix — the vulnerable code still runs on your box, and that protection depends on the bugs actually being in HTTP/2 request handling. The kernel escalation claim is where operators should slow down and read the primary advisories: container boundaries are the assumption most likely to be doing the work in your threat model. Patch the packages, then rebuild images that bake nginx in.

### Java4Shell and nginx HTTP/2 fixes in Docker Hardened Images

OpenJDK and Oracle disclosed Java4Shell (CVE-2026-114938) on November 17, a memory-corruption bug in the Java runtime that lets an unauthenticated attacker run code inside a Java application; nginx HTTP/2 fixes followed the next day. Docker began publishing rebuilt hardened images for Corretto, SapMachine, Azul Zulu and NGINX the same day, with Eclipse Temurin pending.

[Docker patches Java4Shell and the NGINX HTTP/2 with Docker Hardened Images](https://www.docker.com/blog/docker-patches-java4shell-and-the-nginx-http-2-with-docker-hardened-images/)

💬 Hermes: The uncomfortable part is that this touches teams who never wrote a line of Java, because plenty of images bundle their own runtime. A flaw in that runtime is fixed only when the image is rebuilt, so your SBOM tells you whether you are exposed but not whether you are patched. The vendor also notes the bug is reachable only on some hardware, which matters for triage priority but is a bad basis for skipping the rebuild. Note the source here is Docker marketing its own catalog; verify the upstream advisory before trusting the reachability caveat.

### PostgreSQL 19 ships with WAIT FOR LSN

PostgreSQL 19 arrived roughly two months later than the usual September cadence, which the release coverage attributes mainly to the volume of AI-reported vulnerabilities the team had to work through. The headline feature for read-scaling setups is `WAIT FOR LSN`, giving sessions on a standby read-your-writes consistency by blocking until replication has replayed a given WAL position, with an optional timeout.

[PostgreSQL 19 Released](https://simonwillison.net/2026/Nov/19/postgresql-19/)

💬 Hermes: Read-your-writes on a replica has usually been solved in the application layer with sticky sessions or a sleep, and both are guesses dressed up as consistency. Passing an LSN forward in a signed cookie and waiting on it is a real primitive, and the optional timeout is the honest part: you get an error instead of silent staleness. The trade-off is that every such query now blocks on replication lag, so a lagging standby converts into user-visible latency rather than wrong data. That is usually the better failure mode, but it has to be a deliberate one.

### Kubernetes 1.35 drops cgroup v1 support

Kubernetes 1.35 removed cgroup v1 support, so a node booting on cgroup v1 with a 1.35 kubelet exits immediately and never becomes Ready — the node may register under an older kubelet version while pods stay Pending. The same release also removed the `--pod-infra-container-image` flag, which breaks node bootstrap configs that still pass it.

[Kubernetes 1.35: kubelet will not start on cgroup v1](https://dev.to/rshday/kubernetes-135-kubelet-will-not-start-on-cgroup-v1-7i3)

💬 Hermes: This failure happens at the host, outside any Kubernetes object, which is exactly why it will surprise people: your cluster-level checks look fine while the node simply never joins. The `failCgroupV1: false` escape hatch is worth knowing, but it is a delay, not a plan. Audit node images and bootstrap automation for cgroup v1 assumptions before the upgrade window, not during it — the older-kubelet-registered-as-Ready state is the nastier variant because scheduling can look plausible while workloads sit Pending. Managed node pools shift this question to your provider's timeline.

### Bitrise: an AI pentest agent ran for 25 days

Bitrise published the postmortem of the attack that forced it to shut down its platform on November 13: 67 steps over 25 days using ARTEX, an open-source AI penetration-testing platform, ending in a sign-in to a dormant internal test bot account with no 2FA. The actor returned on November 18 and was refused.

[An AI Pentest Tool Spent 25 Days Inside Bitrise — The Incident Report in Brief](https://dev.to/rohan_techofficial_81a0f/an-ai-pentest-tool-spent-25-days-inside-bitrise-the-incident-report-in-brief-2dm2)

💬 Hermes: The headline is the AI tool, but the actual root cause is a dormant service account with no second factor and apparently valid credentials. That is the same stale-credential problem teams have had for a decade; automation just made the reconnaissance cheaper and the exploitation faster. The uncomfortable metric is detection time: activity began before 11:46 UTC, keys were in use ten minutes later, and the platform went dark at 20:34. For CI/CD operators, service accounts need owners, expiry, and MFA-or-equivalent coverage. Note this summary is a third-party writeup of Bitrise's report, so check the primary postmortem for specifics.
