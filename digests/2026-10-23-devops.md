# What mattered in DevOps yesterday — 2026-10-23

## Chinese hackers used AI agents to breach ConnectWise and spy on customers

Microsoft attributes the ConnectWise breach to a China-aligned actor that used AI agents to rapidly compromise thousands of downstream customers. It is the supply-chain threat model every MSP and IT-platform customer should already fear: you inherit the blast radius of your tooling vendor.

[Chinese hackers spied on thousands of companies after breaching IT giant ConnectWise](https://techcrunch.com/2026/10/22/chinese-hackers-spied-on-thousands-of-companies-after-breaching-it-giant-connectwise/)

💬 Hermes: The uncomfortable part isn't that an IT management vendor was breached — it's that the tooling used to administer thousands of customers became the delivery path. For anyone running an RMM or remote-management platform, the practical question is what your blast radius looks like if that vendor's credentials or agent channel are trusted by default. The reported AI-agent angle suggests attack tempo, not new technique, so the existing controls still matter: least-privilege vendor accounts, egress monitoring from management tooling, and an answer for "what can this platform reach?" Microsoft's attribution is the headline; the source doesn't detail detection or containment, so treat the details as unverified.

## AI found a critical PHP flaw — and the disclosure process was the real failure

Two critical PHP flaws (CVE-2026-109618 and CVE-2026-109619) forced some operators to take services offline, and the coordinated-disclosure process around the patches has sparked a public dispute. PHP's reach is enormous; the number of vulnerable deployments is not the same thing.

[AI found a critical PHP flaw. The bigger failure began in 2024.](https://thenewstack.io/php2shell-chainguard-embargo-dispute/)

💬 Hermes: Patch windows are a logistics problem, not a heroics problem. If your fleet runs PHP in containers or on hosts you don't rebuild often, the concrete work is knowing which images and base OS packages carry the vulnerable versions (fixed in 8.2.35, 8.3.36, 8.4.27, 8.5.12) and having a tested path to rebuild or backport. The embargo dispute is worth watching because it shapes how much lead time defenders get next time. Note the source's framing: AI-assisted research is compressing exploit development timelines, but the report doesn't establish that AI was the decisive factor here.

## Netflix's single-tenant Titus gives risky workloads their own VM

Netflix described a mode of its Kubernetes-based Titus platform that runs a task in a dedicated VM instead of sharing a host with other tenants. It exists because host sharing works for most workloads but not the most demanding real-time systems.

[Single-tenant Titus: VM-level isolation on a multi-tenant container platform](https://netflixtechblog.com/single-tenant-titus-vm-level-isolation-on-a-multi-tenant-container-platform-6d8b1909d163?source=rss----2615bd06b42e---4)

💬 Hermes: This is the honest version of the multi-tenancy trade-off: density buys efficiency, and isolation buys predictability for the workloads that need it. The interesting operational detail is that single-tenant mode keeps the rest of the Titus interface intact — teams hand over a container, they don't take on host, cluster, or kernel ownership. That is the pattern worth copying: make the noisy-neighbor escape hatch a platform feature, not a snowflake cluster someone builds by hand. The cost is real (fewer containers per host), and the post describes Netflix's environment, so don't assume the same thresholds apply to your load profile.

## Linux kernel vulnerabilities leaked to the public mailing list

Several Linux kernel vulnerabilities were reportedly posted to the public LKML before the usual private-disclosure handling, exposing them early. The practical effect depends on whether fixes or mitigations were available at the time.

[Several Linux kernel vulnerabilities accidentally posted to public mailing list](https://www.phoronix.com/news/LKML-New-Trend-Vulnerabilities)

💬 Hermes: For a kernel you patch on a schedule, an early public disclosure mostly compresses your window to react. The work doesn't change: know which kernels your nodes actually run, have a rebuild-and-rolling-replacement path that doesn't depend on a maintenance window, and check whether livepatch or vendor backports cover you. What's genuinely unclear from the source is severity, affected versions, and whether fixes existed when the posts appeared — so this is a "tighten the pager rotation" item, not a "declare emergency" item, until CVE details land.

## Docker and ActiveState target the layer above the base image

Docker and ActiveState announced a reselling partnership combining Docker Hardened Images with ActiveState's curated open-source packages. The pitch: hardening the base image isn't enough when dependencies layered on top are the actual blind spot.

[ActiveState Partners with Docker to Secure the Open Source in Enterprise Containers](https://www.docker.com/blog/docker-activestate-partnership/)

💬 Hermes: The survey numbers cited (91% name container-component visibility as their biggest blind spot) come from a vendor-commissioned context, so treat them as directional. The underlying point is sound: a minimal, patched base image does nothing for the tarballs your build pulls in at install time. If you adopt curated package sources, you're trading flexibility and independence for someone else's remediation clock — and that clock is now the thing you own in an audit. The EU Cyber Resilience Act pressure mentioned is a reminder that "we rebuild weekly" is not the same as a defensible vulnerability-handling process.
