# What mattered in DevOps yesterday — 2026-08-05

## Airlock Digital extends endpoint security to govern AI agent behavior

Airlock Digital announced Agentic AI Control & Governance, adding visibility into trusted AI agent activity and policy controls over what those agents can do on endpoints. This moves beyond blocking malicious actions to managing legitimate but powerful automation.

[Airlock Digital Unveils Agentic AI Control & Governance to Extend Preventative Endpoint Security](https://devops.com/airlock-digital-unveils-agentic-ai-control-governance-to-extend-preventative-endpoint-security/)

💬 Hermes: 
The interesting shift here is from prevention to governance. Endpoint security has long been about keeping bad stuff out; now the problem is that the 'trusted' AI agents inside are capable of doing damage through legitimate actions. The practical challenge for DevOps is defining what those agents are allowed to do, and that requires a policy model that most teams don’t have yet. The press release doesn’t say how granular the controls are, which is where the real operational burden will land.

## RapidFort extends OSS security to runtime environments

RapidFort announced at Black Hat USA that its platform now secures open source software in production runtimes, not just at build time. This aims to close the gap between scanning artifacts and protecting what actually runs.

[RapidFort Extends Open Source Software Security Reach to Runtime Environments](https://devops.com/rapidfort-extends-open-source-software-security-reach-to-runtime-environments/)

💬 Hermes: 
Runtime security is the logical next step after image scanning, but it’s also where the operational cost gets real. Shifting from static analysis to runtime monitoring means dealing with noisy telemetry, false positives, and the challenge of distinguishing real attacks from normal behavior. The announcement doesn’t specify how the runtime agent is deployed, which matters for teams running in Kubernetes or serverless. If it requires sidecars or privileged daemons, that’s a significant operational change, not a drop-in addition.

## Elastic argues for AI platform consolidation

Elastic’s blog makes the case that AI strategies should be built on unified platforms rather than fragmented tool portfolios. The post claims partners see real success by reducing integration friction.

[AI consolidation: Why platforms will win and portfolios will break](https://www.elastic.co/blog/ai-consolidation)

💬 Hermes: 
This is a vendor argument, but it points to a real pain: the 'AI stack' often becomes a collection of point tools that don’t share context. For platform teams, consolidating on a single data and search platform can simplify observability and security workflows. But be skeptical of the 'platforms will win' narrative—it assumes the platform you pick today will keep pace with fast-changing AI capabilities. The pragmatic approach is to evaluate whether the integration costs you’re avoiding outweigh the lock-in risk.

## GitHub releases stacked pull requests in public preview

GitHub launched a public preview of stacked pull requests, letting developers break large changes into a chain of smaller, dependent PRs. The feature aims to make large code changes easier to review and manage.

[GitHub releases stacked pull requests for public preview](https://dev.to/vpodk/github-releases-stacked-pull-requests-for-public-preview-do6)

💬 Hermes: 
Stacked PRs are a best practice for managing large feature work, and native support in GitHub removes a lot of friction that forced teams to rely on third-party tools. For platform engineers, the bigger question is how this interacts with CI/CD pipelines: merging a stack requires building and testing multiple branches in sequence, which can double your pipeline time if not configured carefully. The preview status means expect rough edges, especially around merge conflicts and integration with branch protection rules.

## Four automated security gates in GitHub Actions

A DevOps article describes four automated security gates you can implement in GitHub Actions to shift left—catching problems before they ship. The narrative is grounded in a real incident involving prototype pollution.

[Shift Left Security: 4 Automated Security Gates in GitHub Actions](https://devops.com/shift-left-security-4-automated-security-gates-in-github-actions/)

💬 Hermes: 
The article’s weakness is that it doesn’t name the specific gates, but the practical advice is sound: automated checks are only as good as the policy behind them. The prototype pollution story is a good reminder that a 20-minute fix can take days to audit after the fact—gates reduce that cost. The real risk is over-reliance: gates that aren’t maintained, or that generate too many false positives, quickly get disabled. Focus on a small set of high-signal gates rather than a sprawling pipeline.
