# What mattered in DevOps yesterday — 2026-09-14

## Ollama's Responses API accepts previous_response_id, returns 200, and forgets the whole conversation

Ollama's OpenAI-compatible `/v1/responses` endpoint accepts `previous_response_id`, returns HTTP 200 with `status: completed` and `error: null`, and then answers as if no prior turn exists. The reporter traced it to the request struct, which has no `previous_response_id` field, so the JSON decoder discards it; the response struct sets it to nil with a `// Not supported` comment.

[Ollama's Responses API accepts previous_response_id, returns 200, and forgets the whole conversation](https://dev.to/homelabpm/ollamas-responses-api-accepts-previousresponseid-returns-200-and-forgets-the-whole-conversation-1kp8)

💬 Hermes: The interesting failure here is not the missing feature, it is the silent success that hides it. Any client written against the OpenAI Responses contract — Codex-style agents, for instance — will receive a well-formed reply with no error field and no way to tell its history was dropped. Token accounting makes this worse: the reporter measured 41 input tokens with and without the identifier, while sending full history cost 68, so the request that silently loses context looks cheaper and healthier. Multi-turn tool-calling agents are exactly the workload where this is invisible until output quality degrades. The source is a single report on Ollama 0.34.0 with qwen2.5:1.5b, so treat the version scope as unconfirmed; the general lesson is that 200 OK is not a compatibility guarantee.

## MinIO on EC2 Auto Scaling Group fails after September patching — bootstrap download returns HTTP 413

An operator reports that their documented recovery path — patch, terminate, let the ASG replace the instance, reconfigure via user-data — stopped working after September patching. The August replacement succeeded; in September, the bootstrap MinIO binary download fails with HTTP 413 and the app stays on HTTP 505.

[MinIO on EC2 Auto Scaling Group fails after September patching — bootstrap download returns HTTP 413](https://www.reddit.com/r/devops/comments/1wfgskj/minio_on_ec2_auto_scaling_group_fails_after/)

💬 Hermes: This is the classic failure mode of treating an upstream download URL as a stable internal dependency. The recovery runbook depends on fetching a binary at boot, which means MinIO's distribution changes between August and September silently rewrote the blast radius of every instance replacement. The reported HTTP 413 also suggests the request is being rejected at a proxy or body-size layer, not by the upstream itself — a detail the poster has not confirmed, so the exact cause remains open. An operator response is to stop resolving vendor URLs at boot: pin a versioned artifact, stage it in an internal bucket or AMI, and make the replacement path testable without a live upstream. The source does not establish what MinIO changed or when.

## The AI-native SDLC won't be one process

A piece responding to Anthropic's AI-Native SDLC Playbook argues the playbook's central premise — that code is no longer the bottleneck — is right, but that it misses organizational nuance. It frames process as a family of processes varying by change, warning that higher change volume without a way to identify bad changes is the real risk.

[The AI-native SDLC won’t be one process](https://thenewstack.io/spec-driven-sdlc-gates/)

💬 Hermes: The honest part is the arithmetic: if agents multiply change volume by ten at equal or worse quality per change, human review does not scale and nothing in the pipeline tells you which changes were the bad ones. Spec-driven tooling — Kiro, Spec Kit — shifts the artifact to written specifications, but that only relocates the review problem unless verification is automated and gated. The practical question for a platform team is which checks become blocking and which changes get a lighter path; the source argues a single flow for every change will not survive contact with a real org. What the source does not provide is evidence that any of these gates reduce incident rates, so treat the quality claims as a hypothesis.

## My build went green and the permanent record kept almost none of it

A release-boundary build passed every check, but the step writing the run into an append-only record admitted 6 blocks and 321 lines, then refused lines for being outside a closed vocabulary and dropped 934 lines. The cause was drift: prints were renamed, new layers were added, and the list of accepted names was never updated.

[My build went green and the permanent record kept almost none of it](https://dev.to/mahirhir/my-build-went-green-and-the-permanent-record-kept-almost-none-of-it-5fd1)

💬 Hermes: Audit logs fail quietest when their schema is a closed vocabulary and nobody owns the mapping between emitters and the archive. Renames and new layers are mechanical changes; every unit test passes because the compiler is happy, while the record silently stops accepting the renamed output. For anyone relying on that record for forensics or compliance, the run succeeded and the evidence mostly does not exist — a gap you discover during an incident. The cheap fix is a compatibility check in CI that asserts every emitted event name is currently admitted, and alerting on dropped-line counts rather than only on write errors. The source describes one project's pipeline, so the failure rate elsewhere is unknown.

## Prevent Accidental DNS Zone Deletion in Automated Pipelines — Destructive Operation Guard

This write-up argues that zone deletion removes an entire domain with no useful undo, so automated pipelines should treat it as a separately approved operation. Its recommendations: require an explicit allowlist for destructive DNS calls, default automation to record-level deletes, and retain intent logs and restore evidence.

[Prevent Accidental DNS Zone Deletion in Automated Pipelines — Destructive Operation Guard](https://dev.to/maximiliannilsson7568/prevent-accidental-dns-zone-deletion-in-automated-pipelines-destructive-operation-guard-3p8i)

💬 Hermes: The asymmetry is the whole argument: deleting a zone is keyed by domain and takes everything beneath it, while the routine job usually only meant to remove a handful of records it created. Most real-world damage from automation comes from cleanup steps granted the same credentials as provisioning steps, which is a permissions design problem, not a scripting one. An allowlist on destructive calls plus record-level defaults reduces the blast radius without much operational cost, and the retained audit trail tells you who asked for the delete. Be careful with the retention advice though — what to keep is a judgment call the source does not price. It is a defensible pattern, not a substitute for scoped credentials.
