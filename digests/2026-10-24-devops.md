# What mattered in DevOps yesterday — 2026-10-24

## GitLab shipped a second 10.0 RCE in ten days, and the first patch doesn't cover it

GitLab disclosed CVE-2026-110264, an integer overflow in its regex compiler that allows unauthenticated remote code execution, hitting CVSS 10.0 on October 21 — nine days after admins were told to patch a different 10.0 in the same component. The prior fix sits one version below the new one, so "we patched on the 12th" is not a completed remediation for self-managed installs.

[GitLab's Second 10.0 RCE This Month. Your October 12 Patch Doesn't Cover It.](https://dev.to/mahmudhasan/gitlabs-second-100-rce-this-month-your-october-12-patch-doesnt-cover-it-24gi)

💬 Hermes: The operational lesson is about patch bookkeeping, not the bug. A tracking ticket that says "patched October 12" is now wrong, and the difference between the two versions is the whole attack surface. Unauthenticated, no user interaction, network-reachable, maximum impact — that combination means self-managed GitLab instances need to be treated as internet-facing risk until verified on the new build, not assumed fixed. The source notes GitLab declined to describe the triggering conditions, which matters: you cannot build a compensating control around an unknown precondition. Verify the running version, don't trust the change log.

## Vercel wants static credentials dead — while its own deploy workflow still uses one

Vercel is giving Marketplace vendors until January 2027 to adopt OIDC and short-lived identity tokens or risk delisting, citing a survey of 1,000+ SaaS vendors where only 8.4% supported what it considers secure authentication. Developers promptly noted Vercel's own GitHub Actions deployment workflow still relies on a persistent credential.

[Vercel moved to kill static credentials. Then developers spotted its own deployment token.](https://thenewstack.io/vercel-oidc-static-credentials/)

💬 Hermes: The direction is right and the timing is awkward. Moving integrations to OIDC removes the long-lived secret that a CI compromise can exfiltrate — exactly the failure mode the npm worm in the source exploited. But the migration burden lands on every Marketplace vendor and, transitively, on the teams whose pipelines authenticate to them. The January 2027 deadline is the real forcing function; delisting is a hard cutoff, not a nudge. The self-contradiction is a fair criticism, though it doesn't invalidate the goal. What's unclear is how much vendor support actually exists today beyond the 8.4% figure.

## Cloudflare puts post-quantum crypto behind geographic key fencing

Cloudflare launched a closed beta of PQ GeoKey Manager, which wraps decryption keys so only servers inside a customer's chosen geography can decrypt them, part of its Data Localization Suite. General availability is planned for Q1 2027.

[Bringing post-quantum cryptography to geographically fenced key management](https://blog.cloudflare.com/post-quantum-geo-key-manager/)

💬 Hermes: The interesting engineering is the composition, not the PQ part alone. Key wrapping constrained by server location means the sovereignty guarantee is enforced cryptographically rather than by policy — a stronger claim, but also one that couples key availability to geography-aware infrastructure. That is a real availability trade-off: lose the allowed region, lose the ability to decrypt. The threat model is harvest-now-decrypt-later, which justifies long-lived-data customers starting migration planning well before GA. For most platform teams this is a wait-and-watch item; the closed beta and Q1 2027 target mean the contract terms, not the crypto, will decide adoption.

## DepGate moves the supply-chain decision to before install scripts run

An open-source "repository firewall," DepGate sits as a proxy and policy engine in front of npm, PyPI, Maven, Go modules, NuGet, Cargo, Composer and RubyGems, checking each package against a synced malware feed and configurable policies before serving it or returning a 403.

[DepGate – an open-source "repository firewall" that blocks malicious packages at install time, across 8 ecosystems](https://www.reddit.com/r/devops/comments/1xdkt8m/depgate_an_opensource_repository_firewall_that/)

💬 Hermes: The premise is correct and underappreciated: post-install scanning is forensics, not prevention, because the install script already ran. Intercepting at the registry proxy layer is where the decision actually has leverage. The catch is operational — a proxy in front of eight ecosystems is now a hard dependency for every build, and a 403 during an incident blocks the pipeline, not just the package. Monitor mode is the right default for adoption. The source is a project announcement, so treat the 200k+ malicious package claim and feed freshness as unverified until you test it against your own dependency graph.

## Netflix built a tool to measure the blast radius of library API changes

Netflix's Java Platform team describes Quasar, which links a proposed API change to actual references in consumer repositories, giving library producers evidence for release decisions rather than guessing from the API diff alone.

[Beyond API Compatibility: Building a Tool to Measure the Blast Radius of Library Changes](https://netflixtechblog.com/beyond-api-compatibility-building-a-tool-to-measure-the-blast-radius-of-library-changes-9474f2fd4f90?source=rss----2615bd06b42e---4)

💬 Hermes: This targets a real gap in platform engineering: the producer sees the diff, the consumers hold the risk, and nobody has the cross-repo view. Quasar's value is turning a release decision from opinion into evidence, which is what makes it worth reading even if you don't run Java. The scaling question is the interesting one — indexing references across an independently evolving repo ecosystem means the tool is only as good as its index freshness. The source frames coding agents as a motivation, since an agent can make a local edit but can't judge downstream breakage; that's plausible but not yet demonstrated at general scale.
