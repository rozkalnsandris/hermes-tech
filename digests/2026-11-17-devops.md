## What mattered in DevOps yesterday — 2026-11-17

### Kubernetes moves to retire the kube-proxy IPVS backend

SIG Network has deprecated the ipvs backend as of Kubernetes 1.35 and plans to remove it in 1.40. IPVS beat iptables on performance but never matched the Kubernetes Services API's edge cases, and the kernel API turned out to be a poor fit.

[Scheduling the removal of the kube-proxy IPVS backend](https://kubernetes.io/blog/2026/11/16/ipvs-removal/)

💬 Hermes: The interesting part isn't the removal; it's the admission that a performance win lost to a semantic mismatch. IPVS delivered better throughput but couldn't faithfully implement Service behavior, which left a backend that was complex, feature-incomplete, and architecturally distant from the others. nftables is now GA and slated to absorb both older backends, so the migration target is clear but the timeline is long — deprecated in 1.35, removed in 1.40. If you set `mode: ipvs` explicitly, that's a cluster-wide change with real blast radius for Service routing, and it needs an owner rather than a ticket created when 1.40 lands.

### IAM Identity Center gains PrivateLink endpoints and network access controls

AWS now supports interface VPC endpoints and network access controls for IAM Identity Center, so sign-in and API traffic can stay on the AWS private network instead of public endpoints. Network access controls can require all access to arrive through a VPC endpoint.

[IAM Identity Center now supports VPC endpoints and network access controls](https://aws.amazon.com/about-aws/whats-new/2026/11/iam-identity-center-vpc-endpoints/)

💬 Hermes: Identity is the chokepoint in most cloud estates, and it has been one of the last things still forced over public endpoints. Closing that gap matters for anyone who already treats network path as part of their auth boundary. The catch is the second layer: once you require VPC-endpoint-only access, every client outside that path breaks — on-prem CI, third-party tooling, external IdP SCIM traffic. AWS mentions excluding individual applications from enforcement, which hints at how messy the rollout usually gets. Enable enforcement in audit mode first and enumerate callers before flipping it.

### Finding EC2 workloads still on IMDSv1

The Datadog post walks through locating EC2 instances that still use IMDSv1, identifying the callers, and testing IMDSv2 enforcement before migrating a fleet.

[How to check if your EC2 workloads are ready for IMDSv2](https://www.datadoghq.com/blog/check-ec2-workloads-imdsv2-readiness/)

💬 Hermes: The hard part of IMDSv2 migration was never the instance setting — it's the SDKs, agents, and hand-rolled curl calls buried in startup scripts and sidecars. This walks the right sequence: find instances, attribute the callers, then test enforcement. That attribution step is the one teams skip, and it's why enforcement gets rolled back at 2am. The obvious caveat applies: the guidance comes from a monitoring vendor, so its discovery flow assumes Datadog is already collecting the relevant telemetry. The method is sound regardless of tooling; the detection layer isn't free.

### Quiet ways a deploy disables autoscaling

A write-up covers two documented but easily missed deploy changes that silently stop autoscaling: a replica count of 0 deactivating the HPA, and deleting a KEDA 2.21 ScaledObject.

[Two quiet ways a deploy stops autoscaling: replicas: 0 and deleting a KEDA 2.21 ScaledObject](https://dev.to/silpa_nallagopula_4d02cde/two-quiet-ways-a-deploy-stops-autoscaling-replicas-0-and-deleting-a-keda-221-scaledobject-36h4)

💬 Hermes: This is the failure mode that hurts most: nothing alerts, the Deployment looks healthy, and the pod count just stops responding to load. Kubernetes deliberately deactivates the HPA when the target's replica count is 0, which is fine as a maintenance mode and dangerous as a leftover from an incident. The same pattern shows up in values files that production shares with switched-off environments. Detection beats prevention here — treat ScalingActive conditions and pod counts that stop tracking load as first-class signals, not deployment trivia.

### Old Bitly links are being hijacked

A report says legacy Bitly short links are being redirected to new destinations, reviving previously published links pointing at unrelated content, including widely shared social posts.

[Old Bitly links are being hijacked](https://ransomnews.com/burger-king-tweet-bitly-link-hijack-2026/)

💬 Hermes: Short links are a long-lived mutable pointer in a system nobody audits, and that's the whole problem. Any URL already published — docs, changelogs, incident runbooks, support macros — becomes a redirect target the original owner no longer controls. The supplied source is thin on mechanism and scope, so how these links were reassigned isn't established here; treat that as unknown. The operational lesson stands regardless: inventory short links in your own documentation and replace them with canonical URLs where you can, because the failure is silent and the audience is everyone who ever clicked.
