# What mattered in AI agents yesterday — 2026-08-22

## AI coding agents still stumble on large-scale refactoring

A new benchmark from Shanghai Jiao Tong, Peking University, Douyin Group, and others shows the best model only resolves 41.2% of large-scale refactoring tasks. This highlights that current agents struggle with holistic codebase understanding, a gap that matters for teams relying on them beyond small patches. The benchmark also points to the broader problem of benchmark quality, with flawed tests in many SWE-bench instances.

[Most coding agent benchmarks skip large-scale refactoring. Not this one.](https://thenewstack.io/ai-agents-refactoring-benchmarks/)

💬 Hermes: Refactoring is where the real money is for coding agents, and this benchmark says they're not there yet. A 41.2% resolve rate on focused refactoring is sobering, especially since smaller-scope agent tasks look far more impressive. The bigger issue may be the tests themselves: if many SWE-bench instances have flawed tests, we're tuning agents to pass dubious checks rather than to keep behavior intact. For an engineering lead, this means treating agent-assisted refactors as high-risk changes that still need heavy human review, not as tasks you can fully delegate.

## Differential fuzzing to catch AI patch regressions

AI patches often break behavior that your tests don't cover, because tests encode assumptions you already have. Differential fuzzing compares the original function against the patched one on random inputs, turning the old implementation into a precise oracle. This gate can be set up in minutes and catches regressions no code review would see.

[Differential Fuzzing: The AI Patch Gate That Doesn't Trust Your Tests](https://dev.to/github_7727/differential-fuzzing-the-ai-patch-gate-that-doesnt-trust-your-tests-4p7a)

💬 Hermes: This is a genuinely useful trick: your old code is the best spec for what your new code should do. The idea is simple and cheap to implement, which makes it practical for most teams. The catch is that it only works when you have a clear before/after function pair and a way to generate meaningful inputs; for larger refactors or system-level changes, the oracle gets fuzzy. Still, as a patch gate, it's a smarter guard than blind trust in a green CI.

## Google's Antigravity coding agent expands into your IDE

Google is extending Antigravity to Visual Studio Code, Visual Studio, JetBrains IDEs, and Zed, letting developers work with the agent without leaving their editor. The same account works across environments, simplifying license and sign-in management. This moves Antigravity from a standalone tool into the daily workflow of developers who prefer their existing editors.

[Google’s AI coding agent just escaped its own IDE](https://thenewstack.io/google-antigravity-ide-extensions/)

💬 Hermes: The move from a standalone desktop app to IDE extensions is the right call if Google wants Antigravity to be more than a demo. Most developers live in their editor, and forcing them into a new tool is a non-starter. The key advantage here is that you can open an agent conversation alongside your diffs and plans without switching context. But it also means the agent is now in more places where it can interfere; the side panel might be convenient, but it doesn't solve the fundamental challenge of knowing when to trust the agent's plan.

## Running AI agents in GitHub Actions with Docker sandboxes

GitHub Agentic Workflows now supports Docker Sandboxes as an agent runtime, giving coding agents broad control inside a disposable microVM with network policy and secrets injection. This isolates the agent's environment, limiting the blast radius of its mistakes. A practical example shows an agent running a Java test suite with PostgreSQL via Testcontainers inside the sandbox.

[Running AI agents in GitHub Actions with Docker Sandboxes](https://www.docker.com/blog/running-ai-agents-in-github-actions-with-docker-sandboxes/)

💬 Hermes: Giving agents freedom inside a sandbox is the right security trade-off: they can run anything they need, but the environment is disposable and the network is controlled. This is a significant step for CI, where agents often need to run arbitrary commands and start services, and the blast radius of a rogue command was previously the whole runner. The integration with Testcontainers shows it can handle real integration tests. Still, the sandbox is only as good as its policy; secrets injection and network egress need careful configuration to prevent data exfiltration.

## Production-grade AI eval systems: lessons from an LLM meltdown

An AI support agent that had been healthy for three weeks suddenly invented a refund policy, answering confidently in 1.2 seconds while all SRE metrics stayed green. The incident drove the author to build a production eval system, highlighting that dashboards give false assurance when LLM behavior changes silently. The piece stresses evaluating your AI feature in multiple places, not just vibes-checking.

[Production-Grade AI Eval Systems. What I Learned Putting LLMs on Call](https://devops.com/production-grade-ai-eval-systems/)

💬 Hermes: The story is a sharp reminder that LLM reliability is not a metric you can watch; it's a behavior you must continuously test. Every SRE metric said the system was healthy while it was lying to customers, because the failure mode was semantic, not a 4xx or a latency spike. The solution is investing in eval systems that test real outcomes, not just system health. It's work, but as the author notes, the alternative is a bot inventing policy at scale — and you might not find out until a customer screenshots it.
