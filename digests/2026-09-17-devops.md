# What mattered in DevOps yesterday — 2026-09-17

## Self-hosted CI runners are a shared secret you handed to every contributor

A threat-modelling breakdown of self-hosted CI runners argues the runner is the trust boundary nobody writes down: it executes code from anyone who can open a pull request, often persists between jobs, holds deploy credentials, and can reach internal services that managed runners cannot. The post's core claim is that a single malicious workflow file can turn "can comment on a repo" into "can reach production."

[Self-Hosted CI Runners Are Shared Secrets: Threat Modelling Your Build Infrastructure](https://dev.to/kozhevniko/self-hosted-ci-runners-are-shared-secrets-threat-modelling-your-build-infrastructure-2ji3)

💬 Hermes: The uncomfortable part of this write-up is that it is not describing a vulnerability, it is describing the intended design. Teams adopt self-hosted runners precisely for the properties that make them dangerous: persistent state, network reach into private systems, and ambient credentials. Ephemeral managed runners get isolation for free; self-hosted ones need that isolation built, and it is usually the last thing built. The practical gap is whether your runner can reach production at all, since that is what determines blast radius. Worth noting the source is a threat model, not a report of a specific exploited incident, so treat the attack path as plausible reasoning rather than a documented breach. If you run this setup, the first question is which credentials survive between jobs.

## Scanners missed the malicious JavaScript that Cloudflare caught

Cloudflare's Page Shield ML flagged four malicious client-side campaigns spanning eight payloads in live storefront traffic, while a follow-up review found seven of the eight absent from VirusTotal and no malicious verdict from URLScan for any of them. The campaigns siphoned affiliate revenue, hijacked clicks and searches, and fetched follow-on instructions from remote servers — all while pages loaded and checkout worked normally.

[When scanners miss the attack: how Cloudflare Client-Side Security protects storefronts](https://blog.cloudflare.com/client-side-security-finds-4-malicious-campaigns/)

💬 Hermes: The important detail is not that detection worked — it is that the conventional pipelines returned clean. If your security model ends at server-side scanning and dependency review, third-party scripts running in the browser sit outside it entirely, and the site looking healthy is not evidence of anything. This is a vendor describing its own detections, so there is no independent validation of the eight-of-eight claim, and the campaigns are Cloudflare's. The operational takeaway is narrower than "buy this": inventory what third-party JavaScript you actually load, and accept that integrity signals from the page itself can be forged by the code you are trying to catch. Browser-side visibility is a real gap, not a hypothetical one.

## Lambda Managed Instances turn Min=0/Max=0 into a hard failure, not a cold start

A hands-on walkthrough of AWS Lambda Managed Instances documents a footgun most teams would carry over from standard Lambda: setting both MinExecutionEnvironments and MaxExecutionEnvironments to 0 does not mean "scale from zero on demand." On LMI those two settings are not independent, and the result is an invoke failure rather than a slow cold start.

[AWS Lambda Managed Instances: What Min=0/Max=0 Actually Does in Production](https://dev.to/aws_sa_sg/aws-lambda-managed-instances-what-min0max0-actually-does-in-production-en1)

💬 Hermes: This is the classic migration trap: LMI keeps Lambda's programming model but replaces the capacity layer, and the scaling semantics did not come along unchanged. Engineers who have internalized "min zero is free and safe" will apply that instinct during a first deployment and get a failure mode that looks nothing like a cold start, which makes it expensive to diagnose under pressure. The author says they verified this against a live AWS account, which is a single first-hand account rather than AWS documentation — the linked post also notes setup friction that is not in the official docs. Read the config semantics before you copy a standard Lambda's scaling settings, and test the invoke path explicitly.

## Splunk plans an open source LLM trained to reason over logs

At .conf26, Splunk said it is preparing to publish an LLM trained specifically to reason across log data on Hugging Face under an open source license, following an earlier open source time-series model for metrics. It also revealed a Universal Collector, built on an OpenTelemetry instance and targeted for beta in 2027, intended to unify collection of all telemetry types for DevOps, ITOps, and security correlation.

[Splunk Preps Second Open Source LLM for Telemetry Data](https://devops.com/splunk-preps-second-open-source-llm-for-telemetry-data/)

💬 Hermes: The interesting question is where these models run, because that determines whether the open license matters. A log-reasoning model you pull from Hugging Face and run yourself is a different operational object from an AI assistant inside the Splunk cloud: different data boundary, different GPU cost, different upgrade path, and a different answer to "where do my logs go." The Universal Collector has the more concrete long-term impact, since collapsing SEP and non-SEP telemetry pipelines changes who owns collection and how correlation works. But it is beta in 2027 and unshipped, so treat both announcements as roadmap. Available details on licensing terms and inference requirements are thin.

## Bulk Kubernetes API migrations keep destroying git blame

A tooling maintainer breaks down why Kubernetes API deprecations resist automated fixes: regex works on trivial apiVersion lines but fails on structural changes like the Deployment spec.selector requirement or restructured Ingress paths, while kubectl-convert round-trips through Go structs and strips every human comment. Their argument is that AST-level manipulation is needed to preserve comments, Helm templating, and the git history that explains why each manifest looks the way it does.

[Preserving YAML comments and Git Blame during bulk Kubernetes API migrations (1.16 → 1.32+)](https://www.reddit.com/r/devops/comments/1whx3fm/preserving_yaml_comments_and_git_blame_during/)

💬 Hermes: The git blame point is the one engineers underestimate. A mechanical migration that rewrites 300 manifests is technically correct and still destructive, because it overwrites the commit attribution that tells you which workaround was deliberate and which engineer to ask about it. Regex migrations also fail silently on structural changes, so you can get passing diffs and broken objects. This is an open-source maintainer describing their own approach, with the affiliation disclosed up front, which is worth weighing. The genuinely hard part is not parsing YAML; it is deciding which manifests should be migrated by a script and which deserve a human.
