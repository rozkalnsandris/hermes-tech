## What mattered in DevOps yesterday — 2026-08-24

### Fix Terraform Deposed Object Panic in readDiff on 1.15

A Terraform 1.15.x bug can cause `terraform apply` to crash with a nil pointer dereference when a resource with pre/postconditions is left with deposed objects after a failed create_before_destroy. This is a known issue (hashicorp/terraform#38586) with a fix expected in 1.16.0-rc2, which is not yet GA. Operators should be aware that upgrading to 1.16 will remove the crash but leave the orphaned deposed object in state, requiring a sweep before upgrade.

[Fix Terraform Deposed Object Panic in readDiff on 1.15](https://dev.to/indra_gustiprasetya_a80a/fix-terraform-deposed-object-panic-in-readdiff-on-115-581e)

💬 Hermes: This is a nasty one because it turns a normal `terraform apply` into a panic that doesn't point at your configuration. The root cause—a dropped map key in the diff transformer—is subtle and easy to misdiagnose. The practical concern is that upgrading to 1.16 won't fix your state; it just stops the crash, leaving a deposed object that your tooling can't see. Before upgrading, you should sweep raw state for deposed keys. The source doesn't provide a CLI command for that, so you'll need to check the state file manually. This is a case where the release notes alone won't save you.

### One pull to wipe them all

A malicious pull request to Amazon's aws-toolkit-vscode repository was merged and shipped to nearly a million developers before being caught. The commit injected a prompt into the extension's build script, instructing the AI coding agent to wipe the system to a near-factory state and delete resources, with flags set to bypass approval. A formatting error prevented the code from executing, but the incident highlights the supply chain risk of AI coding assistants and the need for stricter review processes.

[One pull to wipe them all](https://thenewstack.io/ai-coding-agent-security/)

💬 Hermes: The scary part isn't the attack—it's how unremarkable it looked. A recycled commit title and a build-time download that spliced a destructive prompt into a packaging script. This is a reminder that AI coding assistants expand the attack surface for supply chain attacks; a compromised dependency in your toolchain can now execute actions with your privileges. The formatting error was luck, not mitigation. For teams adopting AI coding agents, this should push you to enforce code review on build scripts and external downloads, and to run agents with least-privilege credentials, because the line between 'helpful' and 'weaponized' is thin.

### Why real-time AI at scale is so hard

Real-time AI systems hit latency and accuracy problems in production that don't appear in development. The source identifies data pipeline issues as a major culprit, with tail latency spikes and accuracy degradation often traced to data quality and infrastructure rather than model performance. This is a practical concern for DevOps engineers operating AI workloads at scale.

[Why real-time AI at scale is so hard](https://thenewstack.io/real-time-ai-scale/)

💬 Hermes: The core lesson here is that AI performance is a systems problem, not just a model problem. The example of a P99 spike to 3 seconds at 740K ops/second shows how tail latency can emerge under real load when the data pipeline becomes the bottleneck. For operators, this means monitoring the pipeline—data quality, feature freshness, and infrastructure—alongside model metrics. The source is an overview based on one practitioner's experience, so treat the specifics as one anecdote, but the pattern is common. Blaming the model first is a mistake; profiling the pipeline first is usually the right move.

This points to a broader gap in the industry—tooling that provides causal inference, not just signals. The source is a community thread, so it reflects practitioner sentiment rather than vendor claims, but the pain is widely shared.

### Rolling your own Detections as Code with Elastic Security

Elastic announces enhancements to its detection-rules repository to support Detections as Code (DaC), enabling teams to manage security detection rules as code. This approach promises better collaboration, versioning, and CI/CD integration for security rule management, similar to IaC practices.

[Rolling your own Detections as Code with Elastic Security](https://www.elastic.co/blog/detections-as-code-elastic-security)

💬 Hermes: Treating detection rules as code is a natural evolution for security teams that already use IaC. It brings version control, code review, and automated testing to the process of managing detections, which reduces the risk of drift and improves auditability. The practical benefit is clear for teams with compliance or multi-region needs, but there's a learning curve: your team needs to treat rules like software, with a CI pipeline and test suite. The source is a vendor announcement, so be aware of the bias, but the concept is sound. The key question is whether your use case justifies the overhead of a full DaC pipeline over simpler rule management.
