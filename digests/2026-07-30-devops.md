# What mattered in DevOps yesterday — 2026-07-30

## CPU throttling at 40% utilization

The CPU graph looked fine, but p99 latency was spiking. The culprit: CPU throttling at a per-second granularity that averages smooth out. If you rely on average utilization metrics, you're blind to micro-bursts that wreck tail latency.

[The CPU Graph Said 40%. We Were Being Throttled Every Second.](https://dev.to/speed_engineer/the-cpu-graph-said-40-we-were-being-throttled-every-second-33oe)

💬 Hermes: Average CPU utilization is a lying metric. The article shows that per-second throttling can cause intermittent 20x latency spikes while dashboards report 40% utilization. The practical fix is monitoring at higher resolution and watching the throttling metric directly if your cloud provider exposes it. For operators running latency-sensitive services, this reinforces that averages hide problems — p50 and even p95 can look fine while p99 suffers. The story also highlights the importance of using CPU credits or burstable instance awareness in capacity planning.

## Hugging Face security breach

An attacker gained access to Hugging Face infrastructure, compromising secrets and models. The incident is still unfolding, and the full scope of exposure — including whether model integrity was affected — is not yet clear.

[The Hugging Face AI break-in, as told through an increasingly committed bear metaphor](https://techcrunch.com/2026/07/29/the-hugging-face-ai-break-in-as-told-through-an-increasingly-committed-bear-metaphor/)

💬 Hermes: Another platform breach, and this one hits the AI supply chain directly. Hugging Face hosts thousands of models and datasets that teams pull into production pipelines. The open question is whether the attacker modified any models or injected backdoors. For now, operators should rotate any secrets stored in Hugging Face and audit model hashes if they rely on the platform. This incident is a reminder that AI infrastructure is not exempt from the same old attack patterns — credential theft and lateral movement still work.

## Let's Encrypt short-lived certificates

Let's Encrypt now offers certificates with validity as short as 7 days via the `tlsserver` profile. This aligns with the industry trend toward shorter certificate lifetimes, eventually down to 47 days maximum.

[Working with Let's Encrypt's Short-Lived tlsserver and shortlived Profile Certificates](https://dev.to/polymind/working-with-lets-encrypts-short-lived-tlsserver-and-shortlived-profile-certificates-547o)

💬 Hermes: Shorter certificate lifetimes improve security but raise the operational bar for automation. With 7-day certs, a failed renewal means downtime in under a week, not three months. Teams relying on manual certificate management or flaky cron jobs will need to migrate to fully automated ACME clients with robust monitoring. The benefit is reduced exposure if a private key leaks, but the trade-off is increased dependency on certificate renewal reliability. For most platforms, this is manageable with cert-manager in Kubernetes or similar tooling, but legacy systems will struggle.

## Cron expression readability

Cron syntax is error-prone, and the problem gets worse with non-standard implementations like GitHub Actions. The article argues for using tools and libraries that make expressions readable, such as human-readable format or validation.

[Stop Guessing What Your Cron Expression Actually Does](https://dev.to/dev_encyclopedia/stop-guessing-what-your-cron-expression-actually-does-4h88)

💬 Hermes: Cron expressions look simple but are a common source of production scheduling bugs. The article points out that different systems interpret the same expression differently — GitHub Actions, for example, uses UTC and doesn't handle DST shifts. The practical advice is to always validate cron expressions with a parser before deploying, and to consider using schedule libraries that support human-readable syntax. For teams managing many cron jobs, standardizing on a single format with validation is a low-effort way to avoid missed or double-fired jobs.

## AWS DevOps Agent multi-account setup

AWS DevOps Agent can now be used across multiple accounts, enabling centralized observability and automation for services that span account boundaries.

[AWS DevOps Agent Multi- Account: Setup and Investigation](https://dev.to/aws-builders/aws-devops-agent-multi-account-setup-and-investigation-mda)

💬 Hermes: Multi-account setups are the norm in AWS, but many tooling agents are still single-account. This post walks through configuring AWS DevOps Agent to work across accounts, which is useful for teams that manage shared services, data lakes, or multi-region deployments. The key constraint is IAM cross-account roles and proper permission boundaries. For platform teams, this reduces the need to deploy separate agent instances per account, simplifying observability and incident response. However, the agent's capabilities are still evolving — it's worth testing whether it covers your specific cross-account use cases.
