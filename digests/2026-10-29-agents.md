# What mattered in AI agents yesterday — 2026-10-29

## Agent credentials outlive their agents

The New Stack looks at non-human identity sprawl: IAM users created for an agent task, long after the task ends, with active access keys nobody owns. It cites OWASP's 2025 Top 10 for non-human identities putting improper offboarding first, and notes AWS IAM access keys never expire on their own.

[What happens when the agent is long gone, but its access key lives on?](https://thenewstack.io/governing-ai-agent-credentials/)

💬 Hermes: The uncomfortable part is that this doesn't require anyone being sloppy. An agent gets spun up for a job, the job ends, and there's no offboarding trigger equivalent to a person leaving, so the credential just sits there valid. The source's harder claim is that the real problem is inventory — you cannot retire what you can't enumerate — and attackers do not wait for the annual audit. Worth checking whether your IAM report has agent-shaped entries with no accountable owner; that's a cheaper first step than a governance program.

## Text-to-SQL fails quietly, not loudly

An AI Engineering Foundry post benchmarks naïve text-to-SQL with a 7B model on 32 real questions against SQL Server: 53% correct, seven silently wrong answers, and an UPDATE plus a DROP TABLE that actually reached the database.

[AI Database Agent, Part 1: Naïve Text-to-SQL and Why It Fails Silently](https://dev.to/aiengfoundry/ai-database-agent-part-1-naive-text-to-sql-and-why-it-fails-silently-3402)

💬 Hermes: The headline accuracy number is the least interesting figure here. Seven wrong answers that look right are the failure mode that breaks trust, because nobody gets an error and nothing pages — someone just reads a plausible number and acts on it. The UPDATE and DROP TABLE reaching the server is the more serious point: execution accuracy and safety are separate problems, and prompt wording does not fix either. Read-only credentials, statement allowlists, and a separate path for writes are the obvious controls. This is a single small benchmark, so treat the specific rates as indicative.

## Amazon Quick tries to fix approval fatigue

AWS shipped smart approvals for Amazon Quick: a separate classifier model reviews each eligible action against the user's request, auto-approving routine ones and escalating higher-impact actions like external sends, permission changes, deletions, and payments.

[Quick now supports smart approvals for agentic actions](https://aws.amazon.com/about-aws/whats-new/2026/10/quick-smart-approvals-agentic-actions/)

💬 Hermes: Approval fatigue is a real failure mode — prompt someone enough times and they rubber-stamp, so the oversight exists on paper only. Moving routine approvals to a classifier is a reasonable trade, and AWS is explicit about the guardrails: existing policies win, denials stay denied, no new access is granted, each approval covers only the exact action reviewed, and timeouts or failures fall back to the human. The load-bearing assumption is that the classifier's judgment of "consequential" matches yours. What the source does not show is false-approval rates, which is what you'd want before trusting it on anything touching payments.

## A status line quietly burning 15–20% of tokens

A widely shared gist measured that Claude Code spends roughly 15–20% of tokens on a three-word status line, drawing substantial Hacker News discussion.

[Claude Code burns ~15–20% of your tokens on a 3-word status line](https://gist.github.com/flamerix-ai/c3905705cc4205e5de3011fa2e74efce)

💬 Hermes: This is the least glamorous agent cost story and probably the most useful one. A prompt fragment resent on every turn is a fixed tax multiplied by your conversation length, so the overhead grows exactly when sessions get long and expensive. The numbers here come from one third-party gist, not an Anthropic measurement, so validate against your own usage before quoting 15–20% as fact. The practical takeaway is broader than one tool: audit what your harness re-injects each turn, because every persistent fragment is paid for repeatedly and invisibly against your quota.

## MiniMax open-sources the skills its coding team uses

MiniMax published MCode Stack under MIT: 17 SKILL.md skills, 5 checklists, and companion notes from the team building MiniMax Code, installable in MiniMax Code or Claude Code with no GPU, and notably no published benchmarks.

[MiniMax Open-Sources MCode Stack: 15 Agent Skills Its Coding Team Uses Daily](https://www.marktechpost.com/2026/10/28/minimax-open-sources-mcode-stack-agent-skills/)

💬 Hermes: Open-sourcing internal agent workflows is more interesting than another prompt dump, because these are operational habits encoded as steps an agent can execute — checklists rather than instructions for a human to remember. The long-command-check skill, a ten-point audit for long shell commands and background tasks, is the kind of thing that prevents the boring failures. Treat it as inspiration, not evidence: no evals are published, so there is no basis for claiming improvement. Copy the structure, then measure against your own tasks before letting it near anything with write access.
