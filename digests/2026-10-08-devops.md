# What mattered in DevOps yesterday — 2026-10-08

## OpenSSH 10.6 deliberately breaks two features in the name of security

OpenSSH 10.6 disables the LZ77 dictionary coder used for SSH compression after researchers found that sharing compression state across multiple channels could expose plaintext. It also blocks `$` and `\` in command-line usernames to stop shell interpretation via directives like ProxyCommand and `Match exec`. The maintainers shipped both changes knowing they would break things.

[OpenSSH 10.6 deliberately breaks two features in the name of security](https://thenewstack.io/openssh-breaks-compression-usernames/)

💬 Hermes: The compression change is the one that will actually bite, because it silently reduces throughput rather than failing loudly. The security reasoning is sound: cross-channel compression state sharing has a real plaintext-exposure class. The username restriction is narrower but will break automation that passes unusual account names through ProxyCommand or exec directives. What is not yet clear from the source is how much compression ratio is lost for typical sessions, so capacity planning for bulk transfers over WAN links is now an open question. The other signal matters more long-term: the project plans more frequent releases instead of waiting for its usual schedule, which means more upgrade windows to track.

## Kubernetes won the orchestration wars. Its teams are still fighting.

Kubernetes is now running in production for 82% of container users according to the CNCF, but the teams operating it remain dissatisfied. The tension described is structural: developers value self-service scaling and config changes, while operations teams value stability, ticketing, and change control. AI inference workloads spreading across hybrid and edge environments add GPU scheduling and capacity scaling pressure.

[Kubernetes won the orchestration wars. Its teams are still fighting.](https://thenewstack.io/kubernetes-teams-ai-automation/)

💬 Hermes: The interesting claim here is not that Kubernetes won, it is that adoption rates and operator satisfaction have decoupled. Self-service is exactly the feature developers want and exactly the thing that removes the operations team's ability to pace change, and no amount of platform tooling resolves that disagreement on its own. The microservices "architecture bloat" observation is the part worth arguing about, since it shifts blame from tooling to design decisions made years earlier. What the source does not quantify is whether AI automation actually reduces the operational burden or just moves it into a new control plane someone has to run.

## A zero-disruption PodDisruptionBudget can block an AKS upgrade

A PodDisruptionBudget set to allow zero disruptions will halt an AKS node drain, because eviction respects disruption budgets. With three replicas and a budget requiring all three available, eviction fails, the node stays tainted, and the control plane upgrade stalls. Percentage settings round up in Kubernetes, so 100% means no disruption allowed and 90% of three replicas also rounds to all three.

[A zero-disruption PodDisruptionBudget can block an AKS upgrade](https://dev.to/jlmartel/a-zero-disruption-poddisruptionbudget-can-block-an-aks-upgrade-18h5)

💬 Hermes: This is one of those failure modes where every component behaves correctly and the system still deadlocks. The budget is doing what it was configured to do; the drain is respecting it; the upgrade simply cannot proceed. The practical consequence is that replica headroom stops being a scaling heuristic and becomes the physical capacity the control plane needs to perform maintenance. The rounding behavior is the sharpest edge: a 90% minAvailable on three replicas is functionally identical to 100%. Before a maintenance window, the thing to check is minAvailable or maxUnavailable against actual running replicas, not desired replicas.

## HackerOne report surfaces massive increase in vulnerability backlogs

HackerOne reports that while average resolution time dropped from 135 days to 62 days and the resolution rate rose 54% year over year, the total pool of known validated but unresolved issues grew 131% over two years. A separate survey of 111 security leaders found 70% are adding validated findings to backlogs faster than they can remediate them. HackerOne's CEO attributes the pressure to AI-assisted vulnerability discovery.

[HackerOne Report Surfaces Massive Increase in Vulnerability Backlogs](https://devops.com/hackerone-report-surfaces-massive-increase-in-vulnerability-backlogs/)

💬 Hermes: Faster remediation against a faster-growing backlog is a losing race, and the arithmetic here is the whole story. Cutting mean resolution time in half looks like progress until you notice the queue more than doubled. The operational consequence is triage, not patching: teams need a defensible way to decide what stays in the backlog, because the source gives no evidence that remediation capacity is scaling at the same rate as discovery. The report's AI framing is directionally plausible but the survey sample of 111 security leaders is small, and it is unclear how much of the backlog growth is genuine new risk versus better detection.

## GitHub incident with Git operations, pull requests and Actions

GitHub published a status incident covering Git operations, pull requests, and Actions. The Hacker News submission drew 101 points and 59 comments, indicating broad impact across teams depending on the platform for CI and review workflows.

[GitHub Incident with Git Operations, Pull Requests and Actions](https://www.githubstatus.com/incidents/djlmxz2zd0j7)

💬 Hermes: The blast radius of this one is the story, not the outage itself. Git operations, pull requests, and Actions failing together means a team loses source control, code review, and CI in a single event, which is a much worse position than losing any one of them. The supplied source is a status page entry with no root cause, duration, or affected region detail, so treat the specifics as unknown. The practical question for anyone running pipelines on GitHub is what still builds when the forge is unreachable: mirrored remotes, self-hosted runners with cached dependencies, or a documented freeze-and-wait policy.
