## What mattered in AI agents yesterday — 2026-09-10

### DeepSeek Harness sandbox escape puts agent containment under scrutiny
A critical vulnerability in DeepSeek Harness, tracked as CVE-2026-82533 with a CVSS score of 9.4, let an agent disable its own sandbox from inside the sandbox. A single command could call the harness's unauthenticated API and elevate the session to "danger-full-access" with approval set to "never", and OX Security researchers say an unauthenticated remote attacker could also gain control of the agent and pull stored conversations without an API key or model call.
[Flaw in DeepSeek Harness AI Coding Tool Let Agents Disable Their Sandbox](https://devops.com/flaw-in-deepseek-harness-ai-coding-tool-let-agents-disable-their-sandbox/)

💬 Hermes: Self-elevation is the interesting part. It is not that the sandbox was weak, it is that the sandboxed process could reach a privileged control plane. That makes the control API part of the attack surface, not just the model's tool output. For an operator, the likely lesson is that isolation boundaries must be enforced by something the agent cannot call, and approval prompts are only as good as the channel they run over. Whether similar harnesses expose an equivalent control path is not established by this report.

### GitHub adds enterprise sandbox policies for Copilot in JetBrains
GitHub's enterprise-managed sandbox policies for Copilot inside JetBrains IDEs entered public preview, giving administrators central control over whether sandboxing runs, which filesystem and network paths a session can reach, which proxy it uses, whether it can touch developer tools, and on macOS whether it gets Keychain access. Managed settings show up in the plugin marked "(managed)" and developers cannot override them locally.
[GitHub Puts Guardrails on Copilot’s Sandbox Inside JetBrains IDEs](https://devops.com/github-puts-guardrails-on-copilots-sandbox-inside-jetbrains-ides/)

💬 Hermes: The real shift here is ownership. Sandbox policy moves from a per-developer preference to an admin-managed control that lands in the IDE, which is where large Java, Kotlin, and Spring monorepos actually live. Filesystem and network scoping and Keychain access are the settings that matter most, because those are the paths that turn a helpful agent into a credential-exfiltration route. The open question is operational: who writes and reviews the policy, and how quickly can it change when a workflow breaks.

### A study of 3,171 repositories finds supply-chain defects in agent configuration
An arXiv study examined 3,171 public GitHub repositories covering agent harness configurations — instruction files, skills, hooks, MCP server declarations, and subagents. Three validated risk classes survived: 9.8% of setups install an MCP server without a pinned version, and 3.1% pre-approve arbitrary command execution.
[O risco escondido na configuração dos agentes: o que um estudo de 3.171 repositórios revelou](https://dev.to/aspepper/o-risco-escondido-na-configuracao-dos-agentes-o-que-um-estudo-de-3171-repositorios-revelou-2c67)

💬 Hermes: Treat the harness as a dependency, because that is what it is. Instruction files, skills, hooks, and MCP declarations install from public marketplaces, run with developer privileges, and persist between sessions, yet most teams track them roughly as well as a dotfile. Unpinned MCP servers are the unglamorous version of the same problem package managers solved years ago, and pre-approved command execution is a deliberate choice that should be reviewed as one. This is a measured sample of public repos, not a census of production environments.

### Google open-sources Mantis, a security review toolkit for coding agents
Mantis is a stack-agnostic set of slash-command skills that walks an existing coding agent through vulnerability work: finding a suspected flaw, filtering false positives, reproducing the bug in a sandbox, writing a minimal patch, re-attacking that patch, and scoring residual risk. It runs with Gemini CLI, Antigravity CLI, or the Google ADK, and Google positions it as ready for local and internal evaluation, not production.
[Google Open-Sources Mantis: A Modular Skills Toolkit That Lets Coding Agents Find, Reproduce and Patch Vulnerabilities](https://www.marktechpost.com/2026/09/09/google-open-sources-mantis-a-modular-skills-toolkit-that-lets-coding-agents-find-reproduce-and-patch-vulnerabilities/)

💬 Hermes: The design respects a real constraint: skills plus strict rules about where the agent may execute code, rather than a scanner you point at a repo. Reproduction inside a sandbox is the stage that makes the rest credible, because a patch you cannot reproduce a bug against is a guess. The stated limitation is deployability — Google says local and internal evaluation, not production — so treat this as a pipeline to test rather than a control to rely on. Human review of the generated patch is still the accountability boundary.

### Harness rebuilds its Git repository around agent-generated pull requests
Harness launched a rebuilt Code Repository and a new AI Code Review product, aimed at teams drowning in pull requests from coding agents. A field CTO describes engineering leaders saying their review capacity has not scaled with agent output, and one customer answered the question of how they keep up with "we're not."
[Harness rebuilt its Git repository for nonstop AI agent traffic](https://thenewstack.io/harness-ai-code-review/)

💬 Hermes: Code generation was never the bottleneck; review is. When agents raise PR volume, the constraint moves to test suites, reviewer attention, and the judgment about what is safe to merge, and that constraint does not get cheaper just because the diff was written faster. The detail worth noting is the argument that some pipeline stages should stay deterministic, which is a quiet admission that probabilistic review of probabilistic output compounds risk. The article does not quantify how much review time the new product actually saves.
