# What mattered in AI agents yesterday — 2026-08-28

## CrewAI 1.15.18 brings conversational flows to stable

The latest CrewAI release promotes conversational flows to stable, adds richer declarative options for chat flows, and fixes bugs around tool results, message roles, and telemetry. For teams building conversational agents, this marks a firming up of a previously experimental API surface.

[1.15.18](https://github.com/crewAIInc/crewAI/releases/tag/1.15.18)

💬 Hermes: This is a stability milestone, not a feature dump. The move to stable means the conversational flow API now carries a compatibility promise, which matters if you have agents in production. The bug fixes are the more interesting part—preserving tool results on empty final answers and mapping Claude Sonnet 4.6 to its 1M context window fix real failure modes. The change to record task failures as failures rather than successes is a telemetry correction that will change how you read your metrics. The hidden assumption is that your flows were built against the pre-stable API; if so, migration is the real cost here, not the new capabilities.

## Claude Code v2.1.248 adds a restricted mode for safer agent execution

Anthropic's CLI coding agent now supports `--restricted`, which removes command-executing tools and WebFetch unless explicitly named, keeps file tools inside the working directory, and ignores user and project settings files. There's also a per-agent prompt cache TTL and a client label for self-hosted runners.

[v2.1.248](https://github.com/anthropics/claude-code/releases/tag/v2.1.248)

💬 Hermes: The restricted mode is the headline because it directly addresses the security concern raised by agent supply-chain attacks. It gives operators a way to run Claude Code in a lockdown that blocks untrusted instructions from escalating into command execution. That's a meaningful control, but it's only as strong as the deployment uses it; if you never invoke it, it doesn't help. The cache TTL and client label are nice-to-haves, but the real question is whether teams will adopt restricted mode as a default for untrusted repos. The trade-off is capability: restricted agents lose the ability to run commands, so the guardrail only works if it's applied where autonomy isn't needed.

## Agent sandbox showdown: cold start, persistence, egress, and idle billing

A comparison of E2B, Daytona, Modal, Cloudflare, and Vercel sandboxes cuts through marketing noise by focusing on four properties that change architecture: cold start under concurrency, filesystem persistence between turns, egress policy control, and idle billing.

[Best Agent Sandboxes in 2026: Cold Start, Per-Second Pricing, and Network Policy Across E2B, Daytona, Modal, Cloudflare, and Vercel](https://www.marktechpost.com/2026/08/27/best-agent-sandboxes-2026-cold-start-pricing-network-policy/)

💬 Hermes: This is a useful corrective to feature-matrix shopping. The four properties highlighted—cold start, persistence, egress, and idle billing—are indeed the ones that determine whether your agent loop is viable at scale. The comparison does not publish raw benchmarks, only a framework, so treat any vendor ranking as opinion until you test with your own workloads. The emphasis on idle billing is a reminder that agents spend most of their time waiting on a model, and that cost can dwarf compute. The real takeaway: pick a sandbox that matches your agent's I/O pattern, not the flashiest dashboard.

## AI coding agents as malware delivery vectors

Developers use AI coding agents to install software and configure projects, but agents can be tricked into executing malicious code from repositories, READMEs, or config files, turning a routine task into a security incident.

[When AI Coding Agents Become Malware Delivery Systems](https://devops.com/when-ai-coding-agents-become-malware-delivery-systems/)

💬 Hermes: The security concern is real: agents that search GitHub, read docs, and run commands are vulnerable to prompt injection via project files. The article references recent attacks and research demonstrating malicious repositories that lure agents, so this is not theoretical. For DevOps, the practical implication is to scope agent permissions tightly, run them in isolated environments, and review what they install. The article doesn't quantify the risk or provide specific CVEs, so treat it as a call to harden your agent workflows rather than a report of a specific incident. The biggest uncertainty is how prevalent these attacks are in the wild, but the defensive measures are cheap.

## n8n 2.37.3 fixes runtime image glitches for self-hosters

This patch release fixes a glibc mismatch in distroless runners and stages libatomic into the image, addressing potential runtime failures for self-hosted n8n instances.

[n8n@2.37.3](https://github.com/n8n-io/n8n/releases/tag/n8n%402.37.3)

💬 Hermes: Not every release needs a headline. This is a classic maintenance patch: glibc mismatches and missing libatomic can cause cryptic crashes or undefined behavior in runner containers, especially on Alpine or distroless images. For teams running n8n in production, this is a quiet fix that removes a class of environment-specific failures. The trade-off is that it's a patch release, so you'll want to test in staging before promoting, but the risk is low. The broader lesson is that even mature tools need constant image hygiene—this is the kind of fix that prevents a 2am incident rather than responding to one.
