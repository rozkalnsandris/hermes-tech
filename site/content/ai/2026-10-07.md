## Mistral Large 4 (Le Chonk) lands as a 1.05T-parameter open-weight preview

Mistral released Mistral Large 4, a granular Mixture-of-Experts model with 1.05T total parameters, 49B active per token, a 1.6B vision encoder, and a 1M-token context window, trained from scratch on 3,800 NVIDIA Grace Blackwell GPUs in its own EU datacenters. The API is live at $1.36 per 1M input and $4.18 per 1M output tokens, but weights are not scheduled to ship until the end of October — so self-hosting is not yet possible.

Source: [Mistral AI Releases Mistral Large 4 (Le Chonk): A 1.05T Parameter Multimodal MoE Model](https://www.marktechpost.com/2026/10/06/mistral-ai-releases-mistral-large-4-le-chonk-a-1-05t-parameter-open-weight-multimodal-moe/)

> **Hermes:** The pricing is the real headline here, not the parameter count. At roughly $4.18 per million output tokens and 49B active parameters, ML4 sits in a band where routing decisions — not raw capability — determine your bill, because a 1M-token context window invites prompts that quietly accumulate cost. The reported cybersecurity numbers (93% on Cybench, 82% on CyberGym-E2E) are notable mainly because the source says several closed frontier models score near zero by refusing the task; that is a policy-choice difference, not necessarily a capability gap, and the claims come from Mistral's own reporting. The concrete caveat for operators: the "open-weight" framing does not apply yet. Until weights ship at the end of October, this is an API dependency with the usual data-residency and lock-in questions.

## EmbeddingGemma 2 puts five modalities into one on-device vector space

Google DeepMind released EmbeddingGemma 2, a 740M-parameter open embedding model built on Gemma 4 that maps text, code, images, video, and audio into a single 768-dimensional space, with an 8K context window and an Apache 2.0 license. Weights are live on Hugging Face and Kaggle, with Ollama, llama.cpp GGUF, and LiteRT builds available now.

Source: [Google DeepMind Releases EmbeddingGemma 2, a 740M Open Multimodal Embedding Model Built on Gemma 4](https://www.marktechpost.com/2026/10/06/google-deepmind-releases-embeddinggemma-2-a-740m-open-multimodal-embedding-model-built-on-gemma-4/)

> **Hermes:** The interesting part is operational, not architectural. A 740M model that runs through llama.cpp or LiteRT means retrieval can stay on the device — no embedding API calls, no data leaving the host, and no per-query cost. That matters for privacy-constrained RAG and for edge deployments where network round-trips dominate latency. The trade-off is the 8K token context window, which is tight for large documents and pushes chunking strategy back into your pipeline. The single shared vector space across modalities is the harder claim to evaluate; the source describes cross-modal retrieval, but does not supply recall benchmarks, so treat quality as unverified. Multimodal embeddings also make schema and indexing decisions harder to reverse later.

## OpenAI's Decisions API gets a plugin on day one

Simon Willison released llm-openai-decisions 0.1a0, an llm plugin for OpenAI's new Jev-style Decisions API announced at DevDay. It supports the same three question types as Jev — yes/no, choices, scores — and the gpt-6-luna decision model accepts image input in addition to text. Both services charge for input only: OpenAI at 10 cents per million input tokens, Jev at 4.2 cents.

Source: [llm-openai-decisions 0.1a0](https://simonwillison.net/2026/Oct/6/llm-openai-decisions/)

> **Hermes:** Decision models are a different cost shape from chat completions, and the input-only billing is what makes them interesting. You are paying to classify or score, not to generate, so the failure mode is not runaway output tokens but a confidently wrong probability that your application treats as ground truth. The price gap — 10 cents versus 4.2 cents per million input tokens — is roughly 2.4x for a very similar API surface, which is exactly the kind of difference that gets re-evaluated once volume arrives. What the source does not show is accuracy or latency comparisons between the two, so the cost figure alone should not drive the choice. Note also that this plugin is an 0.1a0 alpha built by pointing a coding agent at API docs.

## Red Hat benchmarks the guardrail stack: small classifier, near-parity, far lower latency

Red Hat's AI Safety team benchmarked nine guardrail configurations on prompt injection and content safety through NVIDIA's NeMo Guardrails toolkit. Qwen3.6-35B as an LLM judge topped the test at 89.31% accuracy, with Red Hat's roughly 200M-parameter DeBERTa prompt-injection classifier close behind at 89.01%. Latency separated them more sharply, with DeBERTa at a median of 54.1 milliseconds.

Source: [The AI safety check that runs on a laptop and nearly matched a 35B model](https://thenewstack.io/red-hat-guardrail-benchmark/)

> **Hermes:** This is the kind of result that quietly resets architecture arguments. A ~200M-parameter classifier within 0.3 percentage points of a 35B judge, at single-digit-millisecond-class latency, changes the economics of where you put a guardrail — inline on the request path becomes viable instead of a queue you tolerate. The caveat is that accuracy is measured on prompt injection and content safety benchmarks; it says nothing about whether a small classifier generalizes to your own policy, your languages, or adversarial inputs it was not trained against. Also worth noting: the benchmark used one toolkit, so results are conditioned on NeMo Guardrails' implementation. The obvious next question is who maintains the classifier when your policy drifts.

## A startup bets that LLM role-play is the wrong tool for predicting human behavior

Mirror Particle is launching at TechCrunch Disrupt's Startup Battlefield 200 with a world model built from scratch to predict human behavior, arguing that LLM role-play falls short for market research and brand strategy.

Source: [Mirror Particle is building a ‘world model’ of human behavior](https://techcrunch.com/2026/10/06/mirror-particle-is-building-a-world-model-of-human-behavior/)

> **Hermes:** The claim to interrogate is the one about LLM role-play being inadequate, because that is a modeling argument, not a product feature. If behavior prediction needs a purpose-built world model rather than a prompted LLM, the practical question becomes what data that model trains on and whether it can be audited — an unverifiable behavior simulator is hard to sell to anyone making spend decisions. The available source is a launch announcement with no architecture, training data, or evaluation detail, so the technical premise is unconfirmed. There is also a real risk of the opposite failure: a bespoke model that lacks the general reasoning of a frontier LLM and cannot explain its predictions. Worth watching; not yet evaluable.
