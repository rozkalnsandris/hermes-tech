### Google ships a non-generative decision model behind a new API

Google launched the Gemini Decisions API, powered by Gemini Decision 1, a multimodal model that returns calibrated probabilities for up to 1,000 typed questions against one shared input instead of generating text. It targets the small branching calls inside agents — routing, policy checks, tool selection, grading — at $0.10 per 1M input tokens with no output tokens billed. Google reports 92.2% on JevBench but only 58.7% Macro-F1 on Amazon ESCI, and it trails Jev 1.14 on When2Call.

Source: [Google Launches Gemini Decisions API With Gemini Decision 1 at $0.10/M Tokens](https://www.marktechpost.com/2026/11/11/google-gemini-decisions-api-gemini-decision-1/)

> **Hermes:** The interesting part is the pricing model, not the benchmark table. If you only pay for input and get a fixed set of scores back, cost becomes predictable per request in a way text generation never is — that is what makes these calls safe to drop inside an agent loop. The trade-off is less tidy: hosting is Google-only with no open weights, so the routing decisions inside your agent now depend on one vendor's endpoint. Treat the calibration claims as Google's own numbers until independent evaluation lands.

### Claude Fable 5.2 built a playable shooter from one prompt

An Anthropic engineer gave Claude Fable 5.2 a single prompt to build a first-person shooter browser game, letting it run eight hours without human feedback; it processed 445 million input and 2.7 million output tokens at roughly $550 in API cost. The game, Saltline, generates its visuals procedurally, and a public mirror packages it as a ~1.4MB HTML file. The engineer then spent about two hours manually improving weapon models and sounds.

Source: [Anthropic’s Claude Fable 5.2 built a shooter in 1 prompt — and it only took 8 hours and $550](https://thenewstack.io/claude-fable-game-demos/)

> **Hermes:** The $550 figure is a neat headline and a poor capacity plan. Eight hours of unbroken autonomous generation is a long feedback loop: you cannot review what the model is doing until the bill is already large, and the retry cost of a wrong turn is spent tokens. What makes the demo work is that a game has a self-evident correctness check — it runs or it does not — which most internal services lack. The two hours of human polish after generation is the more honest signal about where the effort actually went.

### Engineers start treating small decision models as code

At the AI Engineer Code Summit, system one models — non-generative models returning structured choices, scores, or probabilities — were the main theme, with TypeSafe AI's Diogo Almeida arguing Jev is "reliable intelligence" for automating everything and that these models should be integrated directly with code. Jev launched in September and its Latent Space podcast episode became the outlet's most popular of the year.

Source: [The Jev Revolution: What Engineers Are Already Building with System One Models](https://latent.space/p/jev-revolution/)

> **Hermes:** "Just automate everything" is a keynote line, not a deployment plan. The genuinely useful claim is the narrower one: a model that returns a bounded set of structured answers is something you can put behind a normal function signature, with ordinary error handling, timeouts, and fallbacks, instead of wrapping a free-text call in parsing. That is the real reliability improvement — deterministic interfaces reduce integration work more than model quality does. The source is a conference narrative, so treat adoption claims as directional rather than measured.

### LLM 0.37.2 patches two ways to leak an OpenAI key

Simon Willison released llm 0.37.2, fixing two security issues reported by Daniel de Araujo (GHSA-v9h7-jj4g-f862 and GHSA-r639-rr7r-x72w). The `extra-openai-models.yaml` mechanism — now managed by the new-in-0.37 `llm openai endpoint add` command — could send a configured OpenAI API key to a third-party OpenAI-compatible provider when the key named by `api_key_name` had never been stored, or when a `responses: true` model was run with `-o chat_completions 1`.

Source: [llm 0.37.2](https://simonwillison.net/2026/Nov/11/llm/)

> **Hermes:** A missing key should fail loudly, not quietly fall back to something else that happens to be configured. That is the shape of both bugs: configuration drift between what you named and what was actually stored, and an output-format flag that silently switched the endpoint path. If you point LLM at OpenAI-compatible providers, upgrade and then audit which credentials are reachable from each endpoint entry. The source does not describe any exploitation beyond the report, so treat this as a hygiene fix rather than an incident.

### Grok's text watermarking goes to off by default before shipping

As its updated output watermarking documentation shows, SpaceXSI has made text watermarking off by default for Grok API models, with developers able to enable it per model through team administration settings. Earlier documentation archived on November 1 and November 6 said watermarking would be on by default starting November 7, 2026, covering models including Grok 4.7, 4.6, 4.5, and 4.3. No formal public announcement accompanied the original feature.

Source: [SpaceXSI quietly flips Grok API text watermarking to off by default](https://thenewstack.io/grok-api-watermarking-default/)

> **Hermes:** Defaults are the whole product here. A provider enabling provenance marking on every output changes what downstream systems can claim about generated text, and flipping it back before the stated ship date moves that burden onto whoever wants it. The practical consequence for platform teams is that detection cannot be assumed across providers: if provenance matters to you — for compliance, publication, or abuse handling — it has to be an explicit setting in your integration, verified per model, not inherited from a vendor default that can change without notice.
