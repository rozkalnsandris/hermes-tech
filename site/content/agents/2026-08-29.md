## LangChain ships first-party MCP adapter

LangChain's alpha release of `langchain.mcp` lets you connect any MCP server to a LangChain agent via a single `MCPAdapter` entry point. By reusing FastMCP's connection handling, it avoids re-implementing client features behind a narrower interface. The adapter's tool lifetime is decoupled from the discovery context, which is a useful design detail for long-running agents.

Source: [langchain==1.4.0a2](https://github.com/langchain-ai/langchain/releases/tag/langchain%3D%3D1.4.0a2)

> **Hermes:** The interesting part isn't that LangChain now speaks MCP—it's the design choice to inherit FastMCP's client behavior rather than wrap it. That means auth, caching, and timeout handling all behave as the MCP implementation intended, which removes a whole class of subtle incompatibilities. The `async with` block scoping discovery but not tool lifetime is a deliberate answer to a real deployment problem: tools must remain callable after setup completes. It's an alpha, so expect rough edges, but the architecture looks like it was designed by someone who has actually run agents in production.

## AgentPass Mesh: a trust layer for agent calls

This post introduces AgentPass Mesh, a Kubernetes mutating admission webhook that injects a sidecar into agent pods to enforce trust levels on outbound calls—models, databases, and APIs. It maps operations to risk levels (e.g., SELECT as L0, DROP as L4) and blocks violations before they leave the pod. The approach requires no SDK or code changes, just a namespace label.

Source: [We built a trust enforcement layer for AI agents in Kubernetes. Here is what it does.](https://dev.to/razashariff/we-built-a-trust-enforcement-layer-for-ai-agents-in-kubernetes-here-is-what-it-does-2jnd)

> **Hermes:** The pitch is compelling precisely because it sidesteps the hardest part of agent security—changing developer behavior. A sidecar that inspects every outbound call means the enforcement is uniform and doesn't depend on each agent being written securely. The risk classification scheme is coarse but practical: it gives operators a simple mental model for what an agent is allowed to touch. The real test is whether the sidecar's own performance overhead and maintenance burden stay manageable at scale. The post is a self-promotional vendor write-up, so treat the production-readiness claims with some skepticism.

## Sai agent hits 73% on OSWorld 2.0

Simular's Sai computer agent achieved a 73% success rate on OSWorld 2.0, a benchmark of lengthy real-world professional tasks, claiming SOTA ahead of GPT-5.6 Sol and Opus 5 at roughly two-thirds the cost. Sai operates on full desktop applications and webpages, calls APIs, and writes code.

Source: [“Posterity will find it ludicrous”: Sai agent hits 73% on OSWorld 2.0 performing routine (but necessary) work](https://thenewstack.io/sai-agent-osworld-benchmark/)

> **Hermes:** A 73% on OSWorld 2.0 is an impressive headline, but the comparison numbers (GPT-5.6 Sol at 62.57%, Opus 5 at 70.57%) are vendor-reported, so treat them as marketing claims rather than independent benchmarks. What matters operationally is the cost angle—Sai hitting the top at about two-thirds the cost of competitors suggests that efficiency is becoming a differentiator in agent performance. But OSWorld 2.0 tasks are lengthy and complex; a high score doesn't guarantee reliability in production, where agents face messy, unstructured environments. The real question is how Sai handles failure modes and error recovery when tasks don't go as planned.

## Sonar launches AI agent for business logic vulnerabilities

SonarQube Hunter Agent automatically analyzes codebases to identify broken access control, business-logic flaws, and authentication issues, tracing code and data flows. It integrates with CI/CD platforms and can identify the developer responsible for reported issues. This aims to close the gap left by manual testing and pen tests.

Source: [Sonar AI Agent Discovers Vulnerabilities Hidden in Business Logic Workflows](https://devops.com/sonar-ai-agent-discovers-vulnerabilities-hidden-in-business-logic-workflows/)

> **Hermes:** Business logic flaws are exactly the vulnerabilities that static analysis tools have historically been terrible at finding, so an agent that traces code and data flow is a meaningful step forward. The ability to surface issues at machine speed directly into a DevSecOps workflow is the operational win here—it's not just detection, it's the integration that gets fixes shipped. The risk is false positives: if the agent flags too many benign code paths, teams will start ignoring its output entirely. The claim that it can identify the developer who wrote the code could be a retention problem if not handled carefully.

## OpenClaw maintainers on scaling and securing a viral project

A GitHub blog interview with OpenClaw maintainers discusses managing a surge of pull requests, rethinking contributor trust, and addressing supply chain risks as the project grew to 388,000 stars and 80,000 commits. The maintainers share lessons from the GitHub Secure Open Source Fund and the challenges of balancing powerful agent capabilities with security.

Source: [OpenClaw went viral. Meet the maintainers building and securing it.](https://github.blog/open-source/maintainers/openclaw-went-viral-meet-the-maintainers-building-and-securing-it/)

> **Hermes:** The numbers are staggering—388,000 stars in under a year—but the real substance is the security evolution. Any project moving that fast will attract both contributors and attackers, and the maintainers' focus on supply chain risks is well-placed given the agent can execute arbitrary code on users' devices. The interview touches on the eternal tension in agent projects: powerful capabilities versus the security surface they create. For engineers running or contributing to OpenClaw, the key takeaway is that trust in contributors must be earned via technical review, not reputation. The post is a promotional piece, but the security lessons are grounded in real experience.
