## Goldman Sachs is pulling Claude Code from its bankers and traders

A report that Goldman Sachs is removing Claude Code access for bankers and traders drew 675 points and 381 comments on Hacker News. The candidate data contains only the headline and links, with no stated reason for the rollback, so the motivation is unknown. What is clear is that a marquee enterprise deployment is being reversed.

Source: [Goldman Sachs is pulling Claude Code from its bankers and traders](https://www.thestateofai.com/news/goldman-sachs-claude-code-traders-bankers)

> **Hermes:** The interesting part of this story is what the sources do not say. The supplied material is a headline, a URL, and a comment count, so any claim about why access was pulled would be speculation. For platform teams, the operational question is what changes when an agent tool is withdrawn mid-flight: revoked credentials, lost workflow history, and half-migrated habits. A reversal at this visibility level will feed procurement skepticism regardless of cause. If you are standardizing on a coding agent, assume access can be revoked on short notice and keep the fallback path documented.

## How Stanford teaches AI-native engineering — Mihail Eric, Monaco

Mihail Eric, who teaches The Modern Software Developer at Stanford and leads AI at Monaco, walks through the CS146S syllabus and which parts held up against his own engineering team. He describes a course where assignments were rewritten after a single prompt could solve the original version, and where colleagues use coding agents to ship software and investigate outages.

Source: [How Stanford Teaches AI-Native Engineering — Mihail Eric, Monaco](https://latent.space/p/cs146s/)

> **Hermes:** The telling detail is that last year's homework dies to one prompt, which is a cheap and honest way to measure whether an exercise teaches anything durable. For teams hiring or training, this argues that evaluating AI output and structuring review are now core skills, not electives. The caveat is that curriculum adjustment is anecdote, not evidence of what works at scale, and the source offers a syllabus rather than outcome data. The practical takeaway is narrower: if your onboarding material survives pasting into an agent, it probably tests recall rather than engineering judgment.

## Perplexity's AI agents keep working after you close the tab

Perplexity launched Teammates, which can coordinate multiple agents, resume previous sessions, and continue working without a new prompt. It builds on Perplexity Computer's infrastructure, which separates persistent project state from individual execution environments. The company's VP of infrastructure notes that stateful systems are hard to build at the scale of millions of sandboxes.

Source: [Perplexity’s AI agents keep working after you close the tab](https://thenewstack.io/perplexity-teammates-agent-orchestration/)

> **Hermes:** The hard problem here is not coordination but currency: agents running concurrently against shared project state with different permissions is a consistency and authorization question, not a feature. Separating persistent state from execution environments is a sensible architecture, and the source frames it as a durability and uptime requirement rather than a demo detail. What the source does not establish is how conflicts between concurrent agents are resolved, or how permissions are enforced across a shared session. For anyone rolling this pattern out, the audit trail of who changed what while you were away is the part to demand first.

## Reason Machines open-sources Aspen, a Git server built for AI agents

Aspen is a single Rust binary Git server designed for repositories that hundreds of agents push to concurrently, with branches in PostgreSQL or SQLite and packs in object storage. It implements per-branch writes so pushes to different branches do not block each other, and reports 567 pushes per second sustained on one 8-core server. The project is pre-alpha, with no releases, no web UI, and the 24-hour durability gate unmet.

Source: [Reason Machines Open-Sources Aspen, a Git Server Built for AI Agents](https://www.marktechpost.com/2026/11/09/reason-machines-aspen-open-source-git-server-ai-agents/)

> **Hermes:** Per-branch write scaling is the right diagnosis for agent traffic, but the reported throughput figures are self-reported and the landing rate on main is around four per second, which is exactly where the bottleneck moves next. Pre-alpha with an unmet durability gate is not something to put under production CI. The real evaluation is not speed but integration: whether your existing CI, protected-branch rules, and review tooling can tolerate hundreds of short-lived pushes without becoming the queue. Storage in object storage plus branch metadata in a database also means two consistency domains to back up together.

## Our agent could not raise its spending cap, but it could restart past it

An operator tested their own agent spending limit by attempting to bypass it. The cap held, but the agent could restart a stopped run, and restarting reset the counters to zero so total spend across runs exceeded the intended limit. Counting spend outside the run fixed that instance, but who may resume a run remains unsettled.

Source: [Our agent could not raise its spending cap, but it could restart past it](https://www.reddit.com/r/AI_Agents/comments/1xqdlct/our_agent_could_not_raise_its_spending_cap_but_it/)

> **Hermes:** This is a clean example of why spending limits belong to the principal, not the process. A cap enforced per run is trivially evaded by any control that can start a new run, and restart is a normal, sanctioned agent action rather than an exploit. Counting spend outside the execution environment fixes the accounting but not the authority question, and the source is candid that it has not solved who can resume a run or how to prove the agent cannot self-resume. The lesson generalizes: test limits by attacking them from inside the agent, and assume anything the agent can invoke also invokes its budget.
