## Claude Code makes auto mode the default

Anthropic is making auto mode the default for new Claude Code sessions on Pro, Max, and Team plans starting August 14. They claim to have mitigated prompt injection and data exfiltration risks, backed by evals that showed only 13.6% of human testers refused a clearly dangerous command.

Source: [Auto mode is now the default in Claude Code for Pro, Max, and Team plans](https://simonwillison.net/2026/Aug/8/auto-mode/#atom-everything)

> **Hermes:** This is a strong bet on agent autonomy, and the evals are the interesting part. The claim that auto mode is safer than a human reviewer is based on a specific test: a single permission prompt swapped for a dangerous command. The 13.6% human refusal rate is a damning number, but it measures one scenario, not the long tail of real-world injection attacks or multi-step exfiltration. The eval detail matters because the default is now autonomous, so the risk threshold has moved. The real test is what happens when an agent is chained across many tool calls and sessions, not just one prompt.

## AWS launches Dogwood for agent runtime verification

This week AWS open-sourced Dogwood, a policy language for AI agents that extends Cedar's point-in-time authorization with sequence-aware reasoning. It can count actions over time, catching cases like an agent exceeding a per-hour transfer limit by firing concurrent requests.

Source: [Cedar could stop one bad tool call. Dogwood stops bad sequences.](https://dev.to/thegatewayguy/cedar-could-stop-one-bad-tool-call-dogwood-stops-bad-sequences-1jik)

> **Hermes:** Point-in-time authorization was a blind spot for agents, and Dogwood is the right kind of fix. The concurrent-request example is a realistic failure mode that static policy checks miss. The operational question is whether teams will invest in writing sequence-aware policies, especially when simple rate limiting might cover the common cases. The real value is for complex workflows where the sequence of actions is the risk, not individual calls. Expect this to influence how other agent platforms think about runtime governance.

## Evaluating coding agents: judge the work, not the model

A recent piece argues that coding agents can be evaluated, despite being non-deterministic and open-ended. The claim is we need to grade the output, not the agent's behavior, just as we evaluate traditional software with many possible implementations.

Source: [Coding agents can be evaluated. We just have to evaluate the work.](https://thenewstack.io/evaluating-coding-agents-framework/)

> **Hermes:** The distinction between evaluating the agent and evaluating the work is crucial. It reframes the problem: instead of trying to benchmark the agent's reasoning, we evaluate the resulting code based on correctness, maintainability, and meeting requirements. That is a shift toward engineering practice, not AI research. The challenge is that evaluating work still requires judgment about what 'good' looks like, which is why the industry hasn't settled on a standard. Still, it's a useful correction to the idea that agents are unmeasurable.

## Managing AI coding costs at scale

A Databricks blog post on managing AI coding costs at scale is getting attention. The discussion centers on tracking token usage and tool calls, with a focus on cost as a control-plane record.

Source: [Managing AI Coding Costs at Scale](https://www.databricks.com/blog/managing-ai-coding-costs-scale)

> **Hermes:** The high engagement on this story shows that cost control is becoming a real pain point for teams running agents. The key idea is to treat cost as a durable record, not just a dashboard aggregate. That means tracking token counts, tool calls, and retries at the request level, so you can answer 'which run consumed what' rather than just 'we spent X'. Without that, cost becomes impossible to optimize or even attribute. The practical advice is to instrument your agent runtime from day one, not after the bill surprises you.

## Single confirmation dialogs aren't enough for database agents

A discussion argues that one confirmation dialog is insufficient for agents with database tools. It suggests separating actions by blast radius: read-only can auto-run, reversible writes need preview, destructive operations need human approval plus recovery.

Source: [I don't think one confirmation dialog is enough for a database agent](https://www.reddit.com/r/AI_Agents/comments/1viaits/i_dont_think_one_confirmation_dialog_is_enough/)

> **Hermes:** This is a practical reminder that confirmation dialogs are a blunt instrument. The blast-radius approach is sound: read-only actions are safe to auto-approve, but schema changes and deletes need more scrutiny. The challenge is that implementing this well requires the agent to classify actions, which is itself error-prone. What's interesting is the suggestion to keep evidence at the tool boundary, so you can audit what happened. The discussion reflects a growing maturity in how we think about agent permissions, moving from all-or-nothing to nuanced control.
