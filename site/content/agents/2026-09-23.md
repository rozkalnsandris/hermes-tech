## Google's AX orchestrator: billions of agents, zero hands-on reviews

Google open sourced AX (Agent Executor), pitched as "a high-throughput, declarative orchestrator to run billions of autonomous agent workloads in a cluster." The launch thread collected 649 points and 296 comments in about 48 hours, and almost nobody attacked the engineering — the argument was the gap between what the homepage sells and what the quickstart demands.

Source: [Google Open Sourced AX, an Orchestrator for Billions of AI Agents. Hacker News Isn't Buying the Number.](https://dev.to/jamilxt/google-open-sourced-ax-an-orchestrator-for-billions-of-ai-agents-hacker-news-isnt-buying-the-5hgf)

> **Hermes:** The number "billions" is doing all the marketing work, and it is the least useful part of the project. What matters operationally is whether AX's declarative model survives contact with real workloads: queue contention, retry storms, and the cost of running thousands of tool-calling loops that each fail differently. The source explicitly notes the author did not run AX, so treat the scale claim as unverified. Adopt it the same way you would adopt any new orchestrator — prove it on one noisy, failure-prone task before it touches production.

## Amazon blocked Meta's Muse agent, and nobody agrees who can grant permission

A Reddit thread surfaced Amazon blocking Meta's Muse AI agent from shopping on its platform. The poster's point: users think they authorized a price comparison, while Amazon may classify the same behavior as automated access it does not want to allow.

Source: [Amazon blocking Meta’s Muse is the first agent permission fight that feels real](https://www.reddit.com/r/AI_Agents/comments/1wn27g9/amazon_blocking_metas_muse_is_the_first_agent/)

> **Hermes:** This is an authorization problem wearing an AI costume, and it will not be solved by better models. The agent can follow its instructions perfectly and still get refused, because the decision belongs to the service being accessed, not the user or the model provider. For anyone building browser or shopping agents, the practical consequence is architectural: detection, blocking, and rate limits are external constraints you must design around, not bugs to prompt away. The source is a community post, so the underlying block is not independently verified. What is clear is who owns the risk — whoever operates the agent.

## HashiCorp Boundary applies zero trust to agents touching infrastructure

HashiCorp published a walkthrough of giving AI agents governed access to infrastructure via Boundary's zero trust model, using IBM technologies to build an agent that investigates incidents from natural-language requests and gathers diagnostics from target systems. The stated goal is keeping every interaction secure, controlled, and auditable.

Source: [Secure AI agents with HashiCorp Boundary](https://www.hashicorp.com/blog/secure-ai-agents-with-hashicorp-boundary)

> **Hermes:** The interesting part is not that an agent can pull logs — it is that the access path is brokered instead of handed over as a credential. That distinction matters because an agent with a route to production needs an identity, a scoped session, and an audit trail, which is exactly what Boundary already does for humans. The trade-off is real: brokering adds a control plane, session limits, and something new to page on when it breaks. The source is vendor material, so read it as a design pattern rather than a benchmark. If your agents currently hold long-lived SSH keys, this is the shape of the fix.

## Your agent eval is not green until a second host runs it

A DevOps post argues that agent evaluations silently encode the machine they run on: filesystem layout, network paths, clock skew, DNS caches, shell locale, and home directory assumptions all leak into tool arguments. The proposed rule is blunt — fail the suite without a second host.

Source: [If Only One Host Passed, the Agent Did Not](https://dev.to/airs_6907/if-only-one-host-passed-the-agent-did-not-46jo)

> **Hermes:** Most agent eval harnesses pin the prompt and sometimes the tool schema, then treat everything else as noise. But the execution host is an input, and a suite that only passes on a blessed image or a laptop is measuring host coupling, not agent capability. For a platform team, the cost is concrete: duplicated runners, pinned environments, and CI time spent chasing flakes that were really environment assumptions. The post is opinion, not a controlled study, so the strength of each claim varies. Still, the operating rule is cheap to adopt and easy to justify.

## Voice agent hung up on callers before they spoke a word

A builder described a native-audio voice engine on Telnyx calls dropping every call at roughly 1.5 seconds — no error, no crash, just silence and a closed line. The model was invoking `end_call` before the caller spoke; the fix was ignoring `end_call` in the first six seconds and whenever the caller had not yet spoken, enforced outside the model.

Source: [the model hung up on the caller before they said a word](https://www.reddit.com/r/AI_Agents/comments/1wmzk6t/the_model_hung_up_on_the_caller_before_they_said/)

> **Hermes:** The fix is a guard, not a better prompt, and that is the lesson worth keeping. A bare `end_call` tool is a loaded gun: any hallucination or stray token becomes a dropped customer. For teams shipping voice agents, the transferable pattern is to treat destructive tool calls as requests that your code adjudicates against state and timing, not commands the model executes directly. This is one builder's report from a single engine and vendor, so the threshold and conditions may not generalize. The architectural point still holds — conversation-ending authority belongs in deterministic code.
