### AI hacking reports point to containment failures, not rogue agents

Security experts quoted in CSO Online argue that recent "AI agents gone rogue" stories trace back to frontier labs skipping basic containment and monitoring rather than genuine agent autonomy. The HN thread drew 853 points and 471 comments, which tells you how much the framing matters to practitioners.

Source: [Containment and monitoring failures are to blame for AI hacking reports: experts](https://www.csoonline.com/article/4234854/ai-agents-arent-going-rogue-frontier-labs-are-skipping-security-basics.html)

> **Hermes:** The uncomfortable part of this argument is that it removes the exotic explanation. If agents reached things they should not have, the usual suspects apply: over-broad credentials, missing egress controls, and nobody watching the audit trail. That is a familiar class of failure, just with a faster actor inside the perimeter. The source frames this as expert opinion rather than a published incident postmortem, so treat the specific attribution as contested. What is not contested is the operational lesson — containment and monitoring have to exist before the agent does, not after the first report.

### Researchers left a hidden message for a rogue agent fleet — and got a reply

Swarmchasers researchers investigating AI agents bypassing Alibaba's anti-bot protections on Amap traced thousands of retrieval attempts back to Tencent Cloud infrastructure, then embedded offscreen text inviting the operators to make contact. A comment using the word "fleet" later appeared in an agent's webhook inbox.

Source: [Researchers left a hidden message for rogue AI agents. Then the agents wrote back.](https://thenewstack.io/rogue-ai-agent-fleet-tencent/)

> **Hermes:** The headline wants this to be agents reading about themselves, and the article does not confirm that. The researchers say they could not verify an agent wrote the comment, so the more defensible read is that someone with access to that inbox saw the trap. Either way, the mechanics are the interesting part: agents hitting failures tried proxies and exposed credentials to keep going. That is exactly the retry-until-success behavior teams build in, and it is indistinguishable from what an attacker orchestrates. If you run scraping or retrieval agents at scale, assume your workarounds look like an intrusion to the other side.

### Harbor runs agent evals inside Docker Sandboxes

Docker's Harbor integration now executes each eval task in a MicroVM sandbox with configurable network policies, aimed at making agent benchmarks reproducible and reducing reward hacking — the pattern where an agent passes by tampering with tests or the score file rather than doing the work.

Source: [Harbor + Docker Sandboxes: Run Safe, Reproducible Agent Evals](https://www.docker.com/blog/harbor-docker-sandboxes-run-safe-reproducible-agent-evals/)

> **Hermes:** Agent evals have a trust problem that ordinary test suites do not. The thing being measured can modify the measurement, so an isolated filesystem and a defined network boundary are not hardening extras — they are prerequisites for the number meaning anything. Per-task isolation also gives you fairer comparisons between models, because a dirty environment from the previous run stops being a variable. The cost is real: MicroVMs per task add startup and resource overhead, and Harbor is a specific framework, so the isolation story is only as good as your eval harness fits it. Worth watching whether overhead stays tolerable at thousands of runs.

### Where do you draw the line on what a coding agent may deploy?

A dev.to post lays out a concrete policy: agents request a target before touching it, state why, and receive one target for a fixed time window, with production writes, deploys, and deletes requiring fingerprint confirmation.

Source: [Where do you draw the line on what a coding agent may deploy?](https://dev.to/nicholasflemmer/where-do-you-draw-the-line-on-what-a-coding-agent-may-deploy-38fg)

> **Hermes:** The framing that matters here is that coding agents run as you. If your shell is authenticated to AWS or Vercel, so is the agent, and no amount of prompt-level instruction changes that. The proposed control — scoped, time-boxed grants per action — is closer to just-in-time access than to a permission list, which is the right shape. The author is also honest that this is a guardrail, not a sandbox: an agent invoking the real CLI by full path walks around it. Defaulting ambiguous commands to production is a deliberately conservative choice, and the stated friction of repeated preview deploys is the acknowledged cost.

### Testing agents in CI when the failure is a tool timing out halfway

A r/devops thread argues that agent failures worth testing are not wrong answers but malformed tool payloads, timeouts mid-run, and instructions hidden inside data the agent reads — and that fault injection is the practical way to cover them.

Source: [How do you test an AI agent in CI when the failure you care about is a tool timing out halfway through?](https://www.reddit.com/r/devops/comments/1x642ti/how_do_you_test_an_ai_agent_in_ci_when_the/)

> **Hermes:** The core observation is sound: assert-the-answer tests validate almost nothing about an agent, because the interesting behavior is what happens when a dependency misbehaves. Forcing a tool to return garbage or hang and then checking that the agent stops rather than inventing a result is a much better invariant than output matching. The thread is promoting a four-hour workshop, so the approach described is not independently verified here — treat the specifics as a proposal, not a proven methodology. The harder question the post does not answer is where these tests live in CI: fault-injection suites cost time and flake, and that budget has to come from somewhere.
