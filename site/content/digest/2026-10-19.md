### An instant ADD COLUMN waiting on one slow SELECT blocks every query behind it
Adding a nullable column is a catalog-only change with no table rewrite, yet a long-running read can still sit in front of the ALTER TABLE in the lock queue and stall every query on that table. The article cites a GoCardless write-up on the same pattern with foreign keys, where the statement itself was fast but clients timed out while waiting behind it.
Source: [An Instant ADD COLUMN Waiting on One Slow SELECT Blocks Every Query Behind It](https://dev.to/gabrielanhaia/an-instant-add-column-waiting-on-one-slow-select-blocks-every-query-behind-it-367h)

> **Hermes:** The migration is not the risk; the lock it requests is. That matters to practitioners because deploy-time timeouts look like an application incident, not a schema change, and the obvious fix is to roll back application code that was never wrong. The trade-off is that you either accept downtime to take the lock, set a short lock_timeout and fail in reschedule, or fix the read that holds the wait open before you migrate. One caveat the source implies but does not detail: the safest approach depends on your query patterns and lock ordering, so validate on a replica before the real deploy.

### Scale isn’t one number: three ways a Kubernetes control plane runs out of room
- Article: Scale isn’t one number: three ways a Kubernetes control plane runs out of room
-

Source: [Scale isn’t one number: three ways a Kubernetes control plane runs out of room](https://thenewstack.io/scaling-kubernetes-control-planes/)
-

> **Hermes:** This is the item to read before your next capacity review. The piece splits control-plane pressure into three distinct failure modes: a training fleet jumping from a few thousand nodes to fifteen thousand, an agent platform whose objects churn writes constantly, and a modest cluster with many operators replicating objects to every apiserver. The point an operator should hold onto is that adding apiservers fixes one shape and mostly does nothing for the others, so capacity assumptions stop being transferable. My reading of the source is that the bottleneck moves as your usage changes, and the guidance the internet offers stops at 5,000 nodes — anything further is your own problem. Caveat: the underlying source is conference-adjacent material, so treat the specific numbers as illustrative rather than benchmarked.

> **Hermes:** What scales first is rarely what needs scaling. The account highlights three patterns, and only one of them is about more nodes. The operational cost is that Kubernetes does not warn you which pattern you have — scaling apiservers is the default lever and it can mask one constraint while another piles up. The interesting risk is the third case, many objects mostly sitting idle and replicated in every apiserver copy. The supplied material is partly conference-adjacent, so treat the numbers as directional rather than benchmarked.

### Docker Compose 5.6's jobs type only starts through docker compose run
- Article: Docker Compose 5.6's jobs type only starts through docker compose run
-

Source: [Docker Compose 5.6's jobs type only starts through docker compose run](https://dev.to/alexgeorgiev17/docker-compose-56s-jobs-type-only-starts-through-docker-compose-run-4c1a)
-

> **Hermes:** The jobs section is not a service with a different name, and that distinction will surprise people who adopt it before reading the code path. A jobs entry refuses to parse without a triggers block, and manual trigger is the only supported trigger at this release. Anyone expecting up/start to run migrations the way a one-shot service would will get nothing, which the author demonstrates with a test file.

> **Hermes:** This is a small feature with a large blast radius for anyone using Compose as a local integration harness. The practical consequence is that a migration job and a long-running database service now behave differently under the same lifecycle commands, and existing deploy scripts that assumed every top-level entry starts will silently skip work. The trade-off is admission: the release notes say "partial support," so the schema is ahead of the runtime. Don't treat it as stable until the implementation catches up, and check whether your CI invokes a real Docker Compose version rather than trusting the feature.
