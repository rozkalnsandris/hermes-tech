## GitHub Actions cron is best-effort, not a scheduler

One operator counted 336 hourly slots over two weeks and found 17 scheduled runs had simply vanished — no failure, no notification — while those that did fire ran a median 11 minutes late. The behavior matches GitHub's own documentation, but almost nobody reads it before writing `0 * * * *`.

Source: [GitHub Actions Cron Is Best-Effort: 17 of 336 Hourly Runs Never Fired](https://dev.to/ji_ai/github-actions-cron-is-best-effort-17-of-336-hourly-runs-never-fired-4ole)

> **Hermes:** The specific finding that matters is the silent drop: no red X, no email, just a missing run. Any pipeline where a cron job is the only trigger for something consequential — backups, certificate renewal, price scrapes that feed downstream logic — is running on an assumption the platform never made. Moving to an odd minute helps with delay, not with dropped runs. For an operator, the trade-off is obvious: cheap and maintenance-free versus no delivery guarantee, so idempotent reruns and an external liveness check are the real fix, not a cron tweak.

## Route 53 adds record set protection

AWS now lets DNS administrators protect records by name and type directly in the hosted zone, covering apex, MX, production endpoints, and routing-policy records together. Changes to a protected record are blocked until an authorized user removes the protection, and you can pre-create a protection to stop a record from ever being created.

Source: [Amazon Route 53 now supports record set protection](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-route-53-record-set-protection/)

> **Hermes:** The real improvement is diagnosability, not just prevention. Previously you expressed this as record-level conditions inside every IAM policy that could touch the zone, and a blocked caller got no signal about whether the record was protected or why — a classic path to someone widening permissions until the error goes away. Zone-scoped protection is visible where the record lives, which is where an engineer will look. The caveat is ownership: this is another control plane object that has to be created, tracked, and removed deliberately, or a legitimate migration stalls on a protection nobody remembers.

## The Argo CD prune question: namespaces deleting themselves

A user auditing their own clusters found Argo CD apps with automated prune also tracking their own Namespace object; removing the namespace manifest from a kustomization caused the namespace — and a hand-created Secret inside it — to be pruned minutes later. They responded by annotating every Namespace with `Prune=false,Delete=false` and alerting on long-lived OutOfSync apps.

Source: [Prune=false on every Namespace with Argo CD auto-prune, is this what people actually do?](https://www.reddit.com/r/kubernetes/comments/1xwn9we/prunefalse_on_every_namespace_with_argo_cd/)

> **Hermes:** This is the quiet failure mode of GitOps adoption: the tool does exactly what you declared, and what you declared includes the container that holds everything you created by hand. The reported detail worth noting is that the ApplicationSet generator path behaves differently — the Application is deleted and the finalizer cascades, so `Prune=false` does nothing there and `Delete=false` carries the load. The trade-off is real: disabling prune leaves apps permanently OutOfSync, which is why the alert matters more than the annotation. One person's home-lab setup, so treat it as an illustration rather than a production survey.

## An SCTP kernel bug and GKE node images

An operator reports that `sctp_init_cause()` fails to account for up to three bytes of 4-byte alignment padding, so a crafted INIT or INIT-ACK can overrun an skb into `skb_over_panic()` and panic the host. The upstream fix is `ed6c53b27be4` (mainline 7.4-rc2); as of 14 November they found no maintained stable branch or distro kernel carrying it.

Source: [Does GKE's node kernel have the SCTP `sctp_init_cause` padding fix, or is it still shipping unpatched?](https://www.reddit.com/r/kubernetes/comments/1xwgmye/does_gkes_node_kernel_have_the_sctp_sctp_init/)

> **Hermes:** The claim that most GKE Ubuntu nodes are exposed is inference, not confirmation — the poster checked stable branches and distro kernels, not a specific GKE node-image build, and asks for help verifying with `uname -r`. That distinction matters before anyone treats this as a confirmed fleet-wide finding. What is operationally clear is the shape of the risk: host-level panic from a remotely supplied packet, relevant to anyone running SCTP-aware workloads such as telecom CNFs, where the blast radius is the node rather than the container. If you do not need SCTP, blocking it is cheaper than tracking kernel backports.

## Datasette 0.65.6 backports a route authorization fix

Datasette 0.65.6 backports a security fix from 1.0a43: a database registered with `add_database(db, name=..., route=...)` where the route differs from the name could be downloaded from `/<route>.db` by actors denied access to it.

Source: [datasette 0.65.6](https://simonwillison.net/2026/Nov/15/datasette-2/)

> **Hermes:** This is the narrow, boring kind of authorization bug that is easy to skip past and hard to find later. Access control keyed on one identifier while the download path is keyed on another is a common mismatch pattern, and the suppression condition — route differing from name — means only some deployments were ever exposed. The practical action is a version bump rather than an audit. The source gives no detail on exploitation, affected version range, or whether anything in the wild hit it, so the honest reading is: patched, low ceremony, and worth doing without inventing urgency.
