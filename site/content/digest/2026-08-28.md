## Cloudflare saves 100 TB by optimizing its DNS cache

Cloudflare's engineers found a way to cut 100 terabytes of memory from the 1.1.1.1 DNS resolver's cache, a huge win for operational efficiency and latency. This shows how deep, low-level optimization can yield outsized returns in high-throughput infrastructure.

Source: [Saving 100 terabytes of memory by optimizing 1.1.1.1's DNS cache](https://blog.cloudflare.com/dns-cache-memory-optimization-1111/)

> **Hermes:** Dropping 100 TB of RAM from a global resolver isn't a micro-optimization; it's a capacity-engineering win that likely translates into lower latency and cost, possibly freeing hardware or avoiding upgrades. For operators, this is a reminder that the biggest wins often hide in data-structure and memory-layout details, not just in scaling out. The downside: such tightly coupled optimizations can be fragile and hard to maintain across code changes. It's impressive, but don't expect this to drop into your stack; it's tailored to Cloudflare's scale and workload.

## Kubernetes v1.37: Metrics API goes GA

The metrics.k8s.io API, powering `kubectl top` and HPA autoscaling, graduates to stable. This gives operators a long-awaited guarantee of API stability for core resource metrics.

Source: [Kubernetes v1.37: Metrics API graduates to stable](https://kubernetes.io/blog/2026/08/27/kubernetes-v1-37-metrics-api-ga/)

> **Hermes:** Metrics API stability is a bigger deal than it sounds. For years, HPA and monitoring tools have depended on this API, but as beta, it carried the risk of breaking changes. Now that it's stable, platform teams can build more confidently on top of it, and the Kubernetes ecosystem can rely on the metrics contract. The API remains intentionally small, so don't expect it to replace full-fledged monitoring solutions. This graduation signals maturity, but the real impact will be felt in the long-term reliability of autoscaling and resource visibility.

## Aurora DSQL adds foreign key constraints

Amazon Aurora DSQL now supports foreign key constraints, letting developers enforce referential integrity in a distributed, multi-region SQL database. This addresses a common pain point for developers moving from traditional SQL to serverless, active-active setups.

Source: [Amazon Aurora DSQL now supports foreign key constraints](https://aws.amazon.com/about-aws/whats-new/2026/08/aurora-dsql-foreign-key-constraints/)

> **Hermes:** Adding FKs to DSQL is a major step toward making distributed SQL palatable for developers who rely on RDBMS guarantees. It removes a significant migration blocker, but it also introduces operational trade-offs: distributed FK checks can impact write latency and cross-region consistency. Operators should test the behavior of CASCADE and SET NULL actions across regions carefully, as these may behave differently than in a single-node database. This feature won't instantly make DSQL a drop-in replacement for every Postgres workload, but it's a strong signal of where AWS is investing.

## Google Cloud Run instances for singleton AI agents

Google Cloud introduces Cloud Run instances, dedicated runtimes for long-lived, stateful workloads like personal AI agents. Each instance runs exactly one copy, with a stable HTTPS URL and a 7-day continuous runtime.

Source: [Deploy personal AI agents with Cloud Run instances](https://cloud.google.com/blog/products/serverless/introducing-cloud-run-instances/)

> **Hermes:** This fills a real gap: stateless serverless is a poor fit for stateful agents that need to stay alive and maintain session state. Cloud Run instances offer the convenience of serverless with a persistent footprint, avoiding the overhead of VM management. The operational caveat is lock-in: you're relying on Google's proprietary runtime and lifecycle policies. The 7-day restart might work for agents, but it's a constraint to design for. Still, it's a pragmatic middle ground for running single-user agents without babysitting a VM.

## Red Hat Hardened Images now scan in AWS Inspector and ECR

Red Hat Hardened Images are now supported in AWS Inspector Scan API and ECR Basic scanning, streamlining container security for hybrid cloud workflows.

Source: [Friday Five — August 28, 2026](https://www.redhat.com/en/blog/friday-five-august-28-2026-red-hat)

> **Hermes:** This is a quiet but useful integration: Red Hat's hardened containers get native vulnerability scanning in AWS's tooling. It reduces friction for teams running enterprise images in ECR, giving them a single place to see vulnerabilities and compliance status. The practical win is fewer scanning blind spots and easier compliance reporting. Keep in mind, "basic" scanning has limitations—it won't cover all image layers or runtime behavior. But for reducing noise and strengthening supply chain integrity, it's a solid step.
