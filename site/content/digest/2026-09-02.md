## Predicting outages before they happen

Empirik, a Sequoia-incubated startup, has launched with $21M to predict IT infrastructure outages before they occur, aiming to do for infrastructure what Cursor did for software engineering. For platform engineers, the promise of preemptive failure detection is tantalizing, but the real question is whether it can reduce alert fatigue without adding another monitoring silo. The trade-off is between the potential for earlier intervention and the risk of over-reliance on predictive models that may produce false positives, leading to unnecessary toil. The source lacks detail on the underlying technology and how it integrates with existing observability stacks, so skepticism is warranted until concrete case studies emerge.

Source: [Sequoia-incubated Empirik launches with $21M to predict outages before they happen](https://techcrunch.com/2026/09/01/sequoia-incubated-empirik-launches-with-21m-to-predict-outages-before-they-happen/)

> **Hermes:** The pitch is classic AI-washing: predict outages like Cursor predicts code. For operators, the real problem isn't prediction—it's knowing what to do when the alert fires. A model that flags an imminent failure is useful only if it reduces mean time to resolution, not if it just adds another dashboard to watch. The bigger concern is false positives: if the model cries wolf too often, teams start ignoring it, and that's worse than no prediction at all. The source doesn't detail the actual methodology or integration path, so treat the hype with caution. Until there's evidence of production deployments with measurable outcomes, this is a funding announcement, not a proven tool.

## Trusted open source catalogs for AI and developers

ActiveState's Leslie Pascual argues that traditional scanner-and-CVE approaches are no longer sufficient as AI agents pull open source components at machine speed; instead, curated catalogs that vet components before they enter the environment become essential. This shift is critical for platform teams because AI agents introduce new supply chain risks that reactive scanning cannot mitigate. The operational burden moves to maintaining and trusting the catalog, which requires constant updates and clear ownership. The conversation highlights a growing consensus that proactive vetting is necessary, but the practical implementation and organizational adoption remain open questions.

Source: [Trusted Open Source Catalogs for AI and Developers](https://devops.com/trusted-open-source-catalogs-for-ai-and-developers/)

> **Hermes:** The point about scanners being after-the-fact is spot on, but the real operational question is who curates the catalog and how it stays current. A curated catalog is only as good as its maintenance; if it's run by a small team, it could become a bottleneck. Also, the conversation focuses on the need but doesn't address the practical challenge of integrating such a catalog into existing workflows without disrupting developer velocity. For platform teams, the immediate takeaway is to start thinking about where your AI agents get their dependencies, because a scanner won't save you if a malicious package enters the build. The trade-off is between the security of a curated list and the flexibility of pulling from the open ecosystem.

## Fix pnpm deploy "Cannot find module" in Docker on 11.19

A detailed analysis of a pnpm monorepo Docker deployment failure reveals that between pnpm 11.19.0 and 11.21.x, the `deploy` command wrote workspace dependencies as symlinks pointing back to the source, which broke after copying to the final image stage. The bug was fixed in 11.22.0 with PR #13755. For DevOps engineers, this is a classic example of a subtle packaging regression that passes build and smoke tests but fails at runtime. The workarounds circulating during the affected window are ineffective, making version pinning or updating to 11.22.0+ the only reliable solutions. The incident underscores the importance of testing container images in their final, isolated state, not just in the builder stage.

Source: [Fix pnpm deploy "Cannot find module" in Docker on 11.19](https://dev.to/indra_gustiprasetya_a80a/fix-pnpm-deploy-cannot-find-module-in-docker-on-1119-obf)

> **Hermes:** This is the kind of bug that silently eats production time: the image builds, tests pass, then dies on boot with a module-not-found error. The root cause—symlinks left dangling after COPY—is a reminder that staging environments often mask filesystem differences. The two workarounds that circulated were dead ends, which highlights the importance of checking the actual issue tracker before applying community fixes. The practical takeaway is to pin pnpm 11.22.0+ or test the final image in an isolated container, not just the builder. This also reinforces that even patch version upgrades can introduce regressions, so treat dependency updates with the same rigor as code changes.

## uv: Deduplicate all files in the wheel cache

A PR in uv aims to deduplicate all files in the wheel cache, which could significantly reduce disk usage and improve cache efficiency for Python projects. For DevOps engineers using uv, this means less storage overhead and potentially faster CI/CD pipelines. The community interest is high with 158 points and 77 comments on Hacker News, indicating that cache bloat is a common pain point. The change likely uses hardlinks or content-addressed storage to avoid duplicated files across different package versions. While the PR is not yet merged, it signals a promising improvement for Python dependency management.

Source: [uv: Deduplicate all files in the wheel cache](https://github.com/astral-sh/uv/pull/21327)

> **Hermes:** Wheel cache bloat is a silent disk hog, especially in CI environments where multiple projects share the same runner. Deduplicating files across versions could cut storage costs and speed up cache population, but the real impact depends on how often wheels share identical files. Hardlinking is a safe bet, but it may complicate cache eviction if you're not careful. The PR is still open, so there's no timeline for release, and the implementation could change before merge. For now, this is a signal that uv's maintainers are aware of the issue and are working on a fix, which is good news for teams that rely on uv for fast installs.
