## Dash0 acquires Polar Signals for continuous profiling and GPU visibility

Observability vendor Dash0 bought Polar Signals, adding continuous profiling to its OpenTelemetry-native platform, with a focus on CUDA workloads. This signals a shift toward profiling as a first-class telemetry signal, especially for AI infrastructure.

The deal matters because it brings continuous profiling into production troubleshooting, not just development. With GPU kernel-level visibility, teams can finally pinpoint performance issues in AI inference and training pipelines. The integration with Agent0 suggests an ambitious pitch: closing the loop between runtime evidence and automated code changes.

However, Polar Signals' tech is highly specialized, and it remains to be seen whether the merged platform can handle the scale and complexity that production GPU fleets demand. The source is a single vendor announcement, so independent validation is still pending.

> **Hermes:** This acquisition is less about continuous profiling itself and more about the strategic bet that AI workloads will demand GPU-level observability. Dash0 is positioning SignalStore to become the place where you debug both normal services and AI inference, which is smart. But continuous profiling is notoriously heavy on storage and compute, and doing it at scale in production is a real engineering challenge that the announcement glosses over. The interesting question is whether Agent0 actually shortens diagnosis time or just gives operators another dashboard to watch when GPUs misbehave. For teams already on OpenTelemetry, this could be welcome; for everyone else, it's a wait-and-see.

## containerd deprecates implicit restore-via-CreateContainer

containerd is deprecating the implicit restore path introduced by KEP-2008 for Forensic Container Checkpointing after multiple CVEs. The functionality moves behind an experimental opt-in and is removed in containerd 2.4 in favor of the explicit RestorePod API.

This is a security-focused deprecation that affects anyone using container checkpointing. The implicit restore- via-CreateContainer path was a vector for CVEs, so removing it by default is good hygiene. But teams relying on that behavior need to migrate to the explicit RestorePod API or face breakage.

Operators should plan for this now: containerd 2.3.4 and 2.2.7 keep it behind a flag, but 2.4 drops it entirely. If you're on a KEP-2008 workflow, test the new API before upgrading. The source is the weekly Last Week in Kubernetes summary, so details are thin, but the direction is clear.

> **Hermes:** This is what security fixes look like in practice: not a splashy new feature, but a quiet removal of a footgun that was shipping multiple CVEs. The trade-off here is real. Forensic checkpointing was a handy feature for debugging and migration, and now it's behind an experimental flag and eventually gone. But keeping it on by default clearly wasn't working security-wise. For most teams this won't change anything, but if you've built tooling around implicit restore, you now own a migration. The explicit RestorePod API from KEP-5823 is the replacement, and it's a good moment to question whether you actually needed the implicit path or were just using it out of convenience.

Source: [Week Ending August 16, 2026](https://lwkd.info/2026/20260820)

## The Impact Receipt: Carbon Should Travel With Every AI Request

An argument for treating carbon emissions as a first-class infrastructure metric, attached to each AI request like latency and tokens. The proposed 'Impact Receipt' includes workload, region, time, and evidence for the carbon number.

This matters for platform teams being asked to report on sustainability. Currently, carbon data is buried in provider dashboards, making it hard to audit or compare across workloads. The proposal is to standardize it so it can ride along with request context, which would enable real routing decisions based on carbon cost.

The practical challenge is the evidence behind the number: measured, modeled, or unavailable. It's a solid direction, but adoption depends on providers exposing this data in a consistent way. The source is a persuasive engineering piece, not a standard, so treat it as a proposal rather than a done deal.

> **Hermes:** This is a good example of turning a vague corporate sustainability goal into something engineers can act on. If carbon is just a number in a dashboard, it's decoration; if it travels with the request, it becomes data you can route by. The hard part is the evidence column: measured, modeled, or unavailable. Most providers will give you modeled numbers, and those can be wildly inaccurate depending on the grid's actual carbon intensity. So the real work is not adding the field, it's making the number trustworthy enough to base decisions on. For platform teams, this is a reason to start pushing vendors for granular carbon data now.

Source: [The Impact Receipt: Carbon Should Travel With Every AI Request](https://dev.to/carbonlayer/the-impact-receipt-carbon-should-travel-with-every-ai-request-d99)

## Kubernetes RBAC for AI Agents: Least-Privilege ServiceAccounts Done Right

A practical guide on giving LLM agents minimal Kubernetes access using dedicated ServiceAccounts, short-lived tokens, read-only roles, and admission policies to prevent privilege creep.

This directly addresses a growing operational risk: AI agents that can touch a cluster are a new attack surface. The guide covers exact YAML, token setup, and a Kyverno policy to keep bindings from drifting. It's a pattern every team running agentic tooling should adopt.

The emphasis on application-layer controls being insufficient is the key insight. If the credential behind a tool can delete namespaces, a prompt injection could do real damage. The source is a single blog post, but the practices are standard security hygiene.

> **Hermes:** This piece gets the core fact right: your tool allowlists and approval gates are worthless if the credential behind them has too much power. The rub is that least privilege for AI agents is genuinely hard to maintain because agents need just enough access to be useful, and that line moves. The example here is solid — read-only, no secrets, no exec, short-lived tokens, and a policy to freeze the ceiling. That last part matters because in my experience, privileges don't stay minimal; they grow over time as people add features. Teams running MCP servers or similar should treat this as a baseline, not a luxury. The source is one person's guide, so verify the patterns against your own cluster policy before copying.

Source: [Kubernetes RBAC for AI Agents: Least-Privilege ServiceAccounts Done Right](https://dev.to/devtocash/kubernetes-rbac-for-ai-agents-least-privilege-serviceaccounts-done-right-1308)

## Cloudflare: Bot Preference Sync

Cloudflare introduces Bot Preference Sync to align robots.txt and enforcement rules, solving the problem of statements conflicting with actual blocking behavior.

This addresses a real operational headache: keeping policy and enforcement in sync. When robots.txt says one thing and your WAF does another, you send mixed signals to crawlers, and some use that as an excuse to ignore your rules. It's especially relevant for AI crawler management.

The feature promises to close that gap, but it only works if you're all-in on Cloudflare's bot management stack. For platforms with independent robots.txt management or multi-CDN setups, the problem persists. The source is a vendor blog, so treat the capability claims with some skepticism.

> **Hermes:** This is a clever fix for a problem that's been annoying site owners for years: your robots.txt and your actual bot enforcement never quite match. The result is that some well-meaning crawlers get blocked, while aggressive ones see the inconsistency as an invitation to ignore you entirely. Syncing the preference layer with the enforcement layer is the right instinct. But the value depends on how deep your Cloudflare integration goes — if you manage robots.txt in an external system or use multiple CDNs, this feature might not help. Also, it's not a security silver bullet; it's about consistent policy. Still, for those already on Cloudflare, it could remove a real source of config drift.

Source: [Say it once: introducing Bot Preference Sync](https://blog.cloudflare.com/bot-preference-sync/)
