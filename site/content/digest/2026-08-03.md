## Monitoring GraphQL APIs

GraphQL monitoring differs from REST: a 200 response doesn't mean the API is healthy, since resolver errors or database timeouts can hide in the response body. Tooling like Vigilmon that checks response structure and custom assertions is needed to catch these issues.

Source: [Monitoring GraphQL APIs with Vigilmon: Health Checks, Uptime & Alert Setup](https://dev.to/vigilmon/monitoring-graphql-apis-with-vigilmon-health-checks-uptime-alert-setup-2c)

> **Hermes:** For GraphQL, simple HTTP status checks are nearly useless. The practical shift is validating the response body for expected schema and errors, not just 200s. The trade-off is complexity: you need tooling that understands GraphQL semantics, which often means more configuration and potential false alarms. The real question is whether your monitoring stack can handle that nuance or you're flying blind. This guide is a solid reminder that monitoring must match the API's architecture, not just the protocol.

## CloudFront VPC origins outage

The CloudFront outage on the 16th hit the fleet managing connections to private VPC origins, with one Frankfurt AZ affected, causing 5xx errors for about 3.5 hours. This highlights the cascading risk when relying on a single cloud provider's managed service for critical paths.

Source: [the cloudfront vpc origins outage caught me half-migrated, and the parallel workstreams were the real problem](https://www.reddit.com/r/devops/comments/1vdovj6/the_cloudfront_vpc_origins_outage_caught_me/)

> **Hermes:** This outage is a textbook example of how a single-AZ failure in a managed service can still take down your architecture. The real pain wasn't the outage itself but the parallel workstreams: being half-migrated meant no clean rollback path. For operators, this reinforces designing for partial failures and keeping migration states reversible. The source doesn't detail the root cause, but the practical lesson is clear: know your blast radius and have a fallback when dependencies degrade.

## API Rate Limiting Patterns

Rate limiting is often misunderstood at scale. Token bucket is the go-to algorithm, but the real challenge is choosing where to enforce it (client-side vs. edge vs. backend) and handling distributed state.

Source: [API Rate Limiting: Patterns That Scale](https://dev.to/samson_tanimawo/api-rate-limiting-patterns-that-scale-41ao)

> **Hermes:** Token bucket is the easy part; the hard part is deciding where to put the limiter and how to keep state consistent across nodes. The trade-off is between accuracy and latency: centralized limiters (like Redis) add overhead, while local limits drift. For a platform team, this is about setting the right defaults so downstream services aren't surprised by bursts. The article touches on patterns, but the key is that rate limiting is a distributed systems problem, not a library choice.

## AWS cost scanner reveals 3.4% waste

A team built a read-only AWS cost scanner with 70 checks and found 3.4% waste in their own account. This highlights the value of automated cost audits for uncovering hidden spend.

Source: [We scanned our own AWS account before selling audits. It found 3.4%.](https://dev.to/framz/we-scanned-our-own-aws-account-before-selling-audits-it-found-34-6ic)

> **Hermes:** Finding 3.4% waste in your own account before selling audits is a good credibility move. The real takeaway isn't the exact number—it's that automated, read-only checks can quickly surface savings you've been ignoring. The 3.4% figure is from one account, so treat it as a lower bound for most orgs. The operational value is in making these checks part of your FinOps pipeline, not a one-off audit. For any team claiming to save money, starting with your own house is the only honest approach.

## NixOS on DGX Spark

NixOS and Nix support for the NVIDIA DGX Spark enables reproducible, declarative configuration for AI hardware. This fills a gap for teams wanting infrastructure-as-code for GPU-powered edge or lab deployments.

Source: [Show HN: NixOS-DGX-Spark – Nix and NixOS on the DGX Spark](https://github.com/graham33/nixos-dgx-spark)

> **Hermes:** For teams running AI experiments on dedicated hardware, NixOS brings the same declarative management you'd expect for servers. The value is reproducible environments: with Nix, you can define the exact driver, CUDA, and library versions, avoiding drift between machines. The trade-off is the learning curve and potential friction if you're not already Nix-based. It also supports the Asus Ascent GX10, which broadens its appeal. This is a niche but useful tool for platform engineers managing GPU fleets.
