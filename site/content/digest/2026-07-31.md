## Stacked PRs are now live on GitHub

GitHub has made stacked pull requests available in public preview, a workflow that lets developers split a large change into a sequence of smaller, dependent PRs. This directly addresses a pain point for teams that struggle with long-lived feature branches and review bottlenecks.

Source: [Stacked PRs are now live on GitHub](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/)

> **Hermes:** The promise here is that stacked PRs shrink review units and get changes merged faster, but the operational cost is real: every stacked branch depends on the ones below it, so rebasing a mid-stack PR can cascade. CI also needs to handle repeated runs across the stack, and not every tool in the pipeline handles partial merges gracefully. Public preview means APIs and defaults can still shift, so it's worth treating this as a pilot for select repos, not a wholesale workflow change. The practical question is whether your code review tooling and merge automation actually understand the dependency chain.

## GCC steering committee announces AI policy

The GCC steering committee has published an official policy on AI contributions to the compiler. With GCC being one of the most critical pieces of open-source infrastructure, how it handles AI-generated code sets a precedent for other projects.

Source: [GCC steering committee announces AI policy](https://lwn.net/Articles/1086041/)

> **Hermes:** For anyone building on GCC, the interesting part is what this policy says about attribution and review burden, not just copyright. If AI-generated patches are treated like any other contribution, the risk is that reviewers spend more time chasing provenance than checking correctness; if they're restricted, the project may miss out on legitimate automation. The source reports the committee's announcement but not the full policy text, so the specific requirements are still unclear. Either way, this is a signal that even conservative infrastructure projects are being forced to define their AI boundaries explicitly.

## Kubernetes v1.36.3 patch release

Kubernetes v1.36.3 has been released, built with Go 1.26.5, and includes fixes for DRA scheduling bugs, a kubelet memory leak regression, server-side apply issues, and kubeadm etcd learner promotion and join resiliency improvements. Patch releases like this are exactly what operators need to keep clusters stable, and the kubelet memory leak is particularly relevant for long-running nodes.

Source: [Week Ending July 26, 2026](https://lwkd.info/2026/20260730)

> **Hermes:** A kubelet memory leak regression is the kind of thing that creeps up slowly, and if you're on 1.36, this is a strong reason to upgrade sooner rather than later. The DRA scheduling fixes also matter if you're using dynamic resource allocation, since scheduling bugs can cause pods to hang or land on the wrong nodes. The etcd learner improvements reduce the risk of cluster instability during control-plane changes. There's no word on whether a serious CVE is included, so the upgrade is more about operational stability than security, but that alone justifies planning the rollout.

## Why your company should (try to) build its own AI SRE

As agentic coding tools accelerate code production, SREs face the unfamiliar problem of debugging code no human fully understands. This article argues that building an internal AI SRE—trained on your own systems and runbooks—may be more effective than relying on generic AI tools.

Source: [Why your company should (try to) build its own AI SRE](https://thenewstack.io/ai-sre-root-cause-analysis/)

> **Hermes:** The core argument is that for AI to actually help with incident response, it needs context that only your own systems provide: runbooks, on-call history, service topology. A generic LLM can't reason about your outage if it doesn't know your stack. But building an AI SRE is a serious project: it means curating that data, maintaining it as systems change, and trusting the model's root-cause suggestions during a live incident. The article doesn't address the validation burden or how to avoid automation bias, so treat this as a direction, not a ready-made solution. Start with a narrow slice, like log triage, before letting it own any part of an incident.

## AI-generated software is forcing yet another platform rethink

At PlatformCon London, a panel on security found that while many teams are using AI to write and review code, few have security systems that account for it. This situation is pushing platform teams to rethink their security tooling and workflows in response to AI-generated code.

Source: [AI-generated software is forcing yet another platform rethink](https://thenewstack.io/ai-code-security-platforms/)

> **Hermes:** The gap between adopting AI code assistants and having security controls that understand them is exactly where new vulnerabilities slip through. Traditional scanners were not built to analyze AI-generated code patterns, and the article suggests that platform teams need to integrate security earlier in the pipeline to keep up. The source reports discussions from a conference panel, so specific tools or solutions are not detailed. The real takeaway is that platform teams should assess whether their current security tooling can handle the code their developers now produce—before an incident forces the question.
