## GitHub's commit surge stresses verification capacity

GitHub now processes 2.9 billion commits monthly, more than double April's volume, and suffered a 7h47m outage on August 17 when central US infrastructure couldn't scale. The platform is adding over 3 million CPU cores and 120 PB of storage and migrating to Azure. The real concern is that almost none of these commits are automatically verified against a running system.

Source: [Commits on GitHub have doubled in four months. Verification capacity has not.](https://thenewstack.io/scaling-ai-code-verification/)

> **Hermes:** The outage is a scaling story, but the uncomfortable number is 2.9 billion commits with no automated check that the change works against a live system. For operators, that means the burst of agent-generated code is landing in branches and merge queues faster than any human or CI can meaningfully validate. Adding CPU and storage fixes transport, not trust. What is not yet clear is whether GitHub will shift verification earlier in the pipeline or just absorb more traffic. If your team relies on GitHub Actions for security checks, the platform's own admission that it can't keep up should change your threat model.

## Aurora MySQL 3.13 brings phased upgrade controls

Amazon Aurora MySQL 3.13, compatible with MySQL 8.0.45, is generally available, including community fixes and Aurora-specific improvements. It supports in-place minor version upgrades and snapshot restore, and can be rolled out across clusters in phases via AWS Organizations Upgrade Rollout Policy.

Source: [Amazon Aurora MySQL 3.13 (compatible with MySQL 8.0.45) is generally available](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-aurora-mysql-313-available/)

> **Hermes:** For teams running Aurora at scale, the important part isn't the MySQL patch level, it's the rollout policy. Coordinating minor upgrades across many clusters manually is where incidents happen. Automating that with the Organizations policy reduces the chance of a fleet-wide surprise, especially if you've been deferring maintenance windows. The trade-off is that automation only helps if your testing pipeline can validate the new version before the rollout reaches production clusters. Snapshot restore offers a safer path, but you still own the verification burden. This is a solid, boring release that removes operational friction.

## Cloudflare BotBase opens operator self-service

Cloudflare's BotBase now lets bot operators check submission status, understand rejections, and update existing entries, moving beyond a one-way submission process.

Source: [BotBase for Operators: A clearer path to joining Cloudflare's directory of bots and agents](https://blog.cloudflare.com/botbase-for-operators/)

> **Hermes:** This is Cloudflare fixing the credibility gap in its bot directory. Previously, an operator could submit a bot and have no idea why it was rejected, which made the directory effectively a black box. Now the transparency loop closes, which should reduce false classifications if operators actually maintain their entries. The practical concern is that this only helps the legitimate operators; the scraping operations that cause real problems won't self-identify. For site owners, the directory is still an allowlist you can choose to trust, but the signal quality improves only if operators bother to update. Worth watching how quickly entries go stale.

## Predictive autoscaling for GPU workloads

Reactive autoscaling fails GPU workloads because GPU nodes take 3–5x longer to provision than CPU nodes, leading to outage windows. Predictive autoscaling anticipates spikes before they arrive.

Source: [Scale before the spike: Predictive autoscaling for GPU workloads on Kubernetes](https://www.cncf.io/blog/2026/08/28/scale-before-the-spike-predictive-autoscaling-for-gpu-workloads-on-kubernetes/)

> **Hermes:** The 45-minute gap between traffic spike and GPU pod readiness is the core problem, and reactive HPA can't close it. The article correctly identifies that the bottleneck is provisioning physics, not configuration. Predictive autoscaling is the obvious answer, but the hard part is building accurate forecasts for spiky, bursty workloads. The author admits their own prediction model required historical data they already had, which suggests this works best for predictable patterns. For teams with irregular demand, the practical path is still to over-provision and accept the cost, or to invest in faster node startup. The trade-off is financial: prediction errors mean paying for idle GPUs.

## OpenAI SDK switches to HTTPX2, subtle breakage possible

The OpenAI Python SDK has replaced httpx with httpx2, a fork maintained by the Pydantic team. While APIs, response models, and timeouts behave the same, certificate verification has changed in a way that passes unit tests but can fail in Docker environments.

Source: [The OpenAI Python SDK Just Dropped HTTPX for HTTPX2. Run This Checklist Before Your Next Deploy](https://dev.to/jamilxt/the-openai-python-sdk-just-dropped-httpx-for-httpx2-run-this-checklist-before-your-next-deploy-3mme)

> **Hermes:** This is exactly the kind of change that ships to production because the test suite stays green. The breakage is in certificate verification, which is environment-dependent and won't show up in mocks or local dev. Any team using the openai package should re-run integration tests against real endpoints and check that custom CA bundles or proxy configurations still work before deploying. The migration guide and HN discussion are useful, but the real lesson is to treat dependency upgrades as production changes, not just version bumps. The fact that the SDK swapped HTTP libraries silently is a warning: read release notes beyond version numbers.
