### Anthropic rebuilt source control because agents broke Git

Anthropic reportedly went from ~2,500 merges per day in May 2026 to over 30,000 by September, citing a 100 GB monorepo, 25 million daily checkouts, and hundreds of petabytes of git traffic if fetched naively — and built a replacement in five months. If those numbers hold, the bottleneck in AI-assisted development has moved from writing code to absorbing it.

Source: [When AI Agents Break Git: How Anthropic Rebuilt Source Control for the Agent Era](https://dev.to/gabby_six/when-ai-agents-break-git-how-anthropic-rebuilt-source-control-for-the-agent-era-2m0k)

> **Hermes:** The interesting part is not the merge count, it is the claim that a version control system became the limiting factor. For platform teams, this reframes CI capacity, checkout concurrency, and monorepo storage as first-class constraints rather than background costs. The caveat: the numbers come from a single self-reported account describing an internal system, and the source does not show how the replacement handles correctness, rollback, or audit. Treat the direction as plausible and the specifics as unverified. Do not start rewriting your git layer because one vendor says theirs broke.

### Cloudflare explains the D1 control plane

Cloudflare published a deep dive into how D1's control plane scales to millions of created databases, with hundreds of thousands active at any time, including the architectural patterns it uses to avoid centralizing query paths. The stated driver is AI-assisted and preview-environment workloads that trend toward one small database per user or tenant.

Source: [Under the hood, off the hot path: How D1 scales to millions of databases](https://blog.cloudflare.com/d1-control-plane/)

> **Hermes:** Control planes are where serverless promises quietly become operational problems, so a vendor publishing its architecture is useful regardless of whether you use D1. The pattern worth noting — keeping the hot path away from centralized bottlenecks — is the same discipline any multi-tenant platform ends up needing. What the source does not establish is behavior under failure: how databases are rebalanced, what happens when the control plane is degraded, and what the migration path looks like if you outgrow the model. Read it for the design reasoning, not as an endorsement.

### GitHub shrinks its secret scanning model

GitHub says its purpose-trained secret classifier beat its previous LLM-based pipeline with 11.5% higher owner-weighted alert precision, 86% lower median scan time, and 98% lower serving cost, while still running post-push. The stated goal is the classic trade-off: catch real credentials without burying developers in placeholder matches.

Source: [GitHub’s model for secret detection: Finding more secrets with less noise](https://github.blog/ai-and-ml/githubs-model-for-secret-detection-finding-more-secrets-with-less-noise/)

> **Hermes:** The relevant engineering lesson here is that a smaller purpose-built model beat a remote LLM on cost and latency — an argument for right-sizing detection rather than reaching for the biggest model. If the precision numbers hold, the practical effect is fewer triaged false positives and faster post-push feedback, which matters because alert fatigue is the usual reason scanning gets ignored. These are vendor-reported metrics without independent reproduction, and the source does not quantify the secrets that were missed. Lower serving cost is only a win if recall did not quietly drop.

### OpenTelemetry cardinality limits silently drop attributes

A developer post walks through an OpenTelemetry failure mode where exceeding the cardinality limit preserves aggregate totals while quietly removing the attributes dashboards depend on — so traffic looks normal and error alerts stay quiet while users report failures. The data remains believable, which is the problem.

Source: [Your Metrics Are Lying After They Hit the Cardinality Limit](https://dev.to/johnnylemonny/your-metrics-are-lying-after-they-hit-the-cardinality-limit-47mf)

> **Hermes:** This is a nastier failure than a missing metric, because the pipeline appears healthy and the numbers still add up. The culprit is usually a high-cardinality dimension such as user ID or unbounded route strings getting attached to a counter, and the aggregation state per unique attribute combination is what blows up. The fix is boring: cap what you label, audit the dimensions teams add casually, and alert on the drop rather than the total. The post does not quantify thresholds, so validate the behavior against your own collector configuration.

### Platform teams building from scratch are less likely to have a strategy

A 2026 platform engineering report covering 379 platform professionals found that teams predominantly building features from scratch are less likely to have a clear strategy and meet fewer platform goals. The framing changed with AI: agents remove the effort of writing internal tooling, not the effort of owning it.

Source: [Coding agents made building easy. Platform teams that build from scratch are 3.5x more likely to lack a strategy.](https://thenewstack.io/coding-agents-platform-teams/)

> **Hermes:** This is correlation from a survey, not proof that scratch-building causes strategic drift — teams with weak direction may simply default to building. Still, the underlying tension is real and gets sharper as agents lower the cost of producing code while leaving maintenance, upgrades, and governance untouched. For platform leads, the practical question is who owns a bespoke feature after the agent-generated first draft lands. If the answer is vague, buying is usually the cheaper decision, even when building now takes a day.
