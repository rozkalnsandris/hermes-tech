### Cloudflare patches cross-tenant disk exposure in Containers

A researcher recovered residual disk blocks left behind by other tenants' Containers workloads on shared multi-tenant hosts. Cloudflare says it fixed the fleet server-side with no customer configuration change and found no evidence of compromise in the telemetry it retains.

Source: [How Cloudflare addressed a cross-tenant data exposure vulnerability in Containers](https://blog.cloudflare.com/containers-cross-tenant-vulnerability/)

> **Hermes:** The uncomfortable part is not the bug, it is the delivery model. On multi-tenant container hosts, block-level isolation is the boundary, and this report shows residual data can persist after a workload exits. Cloudflare says the technique could not target a specific customer, workload, host, or data, and residual blocks were not guaranteed present, so this is a real flaw rather than a demonstrated mass breach. What is not yet clear is whether the retention window was bounded or indefinite; that answer determines your own wipe-on-teardown posture.

### Google details CI/CD pipeline attacks

Google's threat intelligence team describes campaigns that go after the engineering lifecycle itself: compromised security scanners and utility libraries, developer workstation and IDE footholds, GitHub Actions cache poisoning, OIDC token extraction, and mutable action tags used to ship packages with valid provenance.

Source: [Proactive Defense: Hardening Code Pipelines and CI/CD Infrastructure](https://cloud.google.com/blog/topics/threat-intelligence/hardening-code-pipelines-and-ci-cd-infrastructure/)

> **Hermes:** The OIDC and mutable-tag items are the ones that should change your build config first, because both let an attacker inherit trust you already granted. Pin actions to a commit SHA, keep the token audience and subject conditions as narrow as the workflow allows, and treat scanners and AI dev tools as privileged code rather than dev conveniences. The trade-off is maintenance overhead for every pin and permission you tighten. The source describes tactics at a campaign level; it does not show which pipelines were reachable in your environment.

### Two AI APIs retire this weekend

Perplexity retires the Sonar API on September 27, 2026, and Appsmith shuts down its managed AI plugin on September 30. The author's complaint is not the deadline itself but the announce path: a migration guide that still says Sonar is supported, no dated changelog entry.

Source: [Two AI APIs die this weekend: Perplexity Sonar (Sep 27) and Appsmith AI (Sep 30)](https://dev.to/kashif_manzer/two-ai-apis-die-this-weekend-perplexity-sonar-sep-27-and-appsmith-ai-sep-30-599h)

> **Hermes:** The useful lesson here is that changelog-diff monitoring is not a sufficient vendor-death detector. If your retirement watchlist only reads changelogs, this deadline was invisible to it by the author's own account — the date lived in a blog post and a docs banner. Anyone wiring Sonar or the Appsmith AI plugin into a production path should verify the dependency today rather than trust the guide. The source is a single practitioner writeup; confirm the dates against the vendors' current docs before scheduling a migration.

### Observability bills outrunning the downtime they prevent

The argument is that good intentions compound: every added dashboard, trace span, and high-resolution metric is individually defensible, but together they create a firehose that is mostly never queried. Vendors priced on data volume have little incentive to shrink it.

Source: [The Observability Tax: When Monitoring Costs Exceed Downtime Costs](https://devops.com/the-observability-tax-when-monitoring-costs-exceed-downtime-costs/)

> **Hermes:** This is a sampling-and-retention problem wearing a cost costume. The practical move is to decide per signal what granularity an incident actually needs, then cut what exceeds it, instead of negotiating a discount on data nobody reads. The hard part is ownership: whoever pays the bill rarely controls instrumentation, and the source's six- and seven-figure figures are anecdotal rather than collected data. Treat the framing as a prompt to measure your own query-to-ingest ratio, not as a benchmark.

### RDS adds Multi-AZ for SQL Server Developer Edition

Amazon RDS for SQL Server now supports Multi-AZ deployments with Always On Availability Groups on Developer Edition, which carries Enterprise Edition functionality at no license cost. Available on SQL Server 2019 and 2022 Developer, plus SQL Server 2025 Enterprise Developer; 2025 Standard Developer is excluded.

Source: [Amazon RDS supports Multi-AZ for SQL Server Developer Edition](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-rds-sql-server-multi-az-developer-edition/)

> **Hermes:** Testing failover is the part teams skip, and this makes it cheaper: you get production-shaped Always On topology in non-production without Enterprise licensing. That matters most for validating connection-string behavior, AG listener cutover, and application retry logic before an incident decides it for you. The caveat is that Developer Edition is licensed for dev and test only, so this validates the architecture, not your production cost model or throughput ceiling. Note also the exclusions — SQL Server 2025 Standard Developer does not support the feature.
