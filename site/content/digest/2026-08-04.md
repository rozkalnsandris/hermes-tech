## 200 Milliseconds
A new site argues that 200ms is the new performance budget for web interactions. It's a useful heuristic, but the real challenge is knowing which interactions truly need that budget.

Source: [200 Milliseconds](https://200ms.thenodebook.com)

> **Hermes:** The 200ms target is a decent baseline, but it's not one-size-fits-all. For core transactions, you might need far less; for background loads, more. The risk is treating this as a mandate and over-optimizing at the cost of complexity or user value. The underlying message — measure real perceived latency, not just server response — is the part worth remembering. Don't chase a number just because it's round.

## Hardening Claude Code: the Minimum Floor as Config
A deep dive into making Claude Code's safety policies something the agent can't bypass. The author describes failed attempts and solutions using configuration, hooks, and gates.

Source: [Hardening Claude Code: the Minimum Floor as Config](https://dev.to/javatarz/hardening-claude-code-the-minimum-floor-as-config-21lo)

> **Hermes:** If you give an AI agent write access to your repo, you're giving it permission to change its own guardrails. That's the core problem this article tackles. Relying on agents to respect hooks or `--no-verify` is fragile; making them config is smarter. But even config can be edited, so the real question is whether you trust the agent not to. In practice, this means the AI's permissions need to be least-privilege, just like any other tool.
