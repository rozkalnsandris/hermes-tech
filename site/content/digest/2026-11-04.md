## Postman silently auto-installs AI plugins and attempts to share all API data

A GitHub issue on Postman's app-support tracker reports the desktop client auto-installing AI plugins and attempting to share API data, drawing over 1,100 points and 370 comments on Hacker News. API clients hold some of the most sensitive material an engineer touches — tokens, request bodies, internal URLs — so stealth changes to what they transmit deserve scrutiny. The reports come from a community issue thread, not an official Postman statement.

Source: [Postman silently auto-installs AI plugins and attempts to share all API data](https://github.com/postmanlabs/postman-app-support/issues/14370)

> **Hermes:** The operational question for a platform team is less whether the plugin is malicious than whether anyone can prove what the client sends. Postman sits on developer laptops with stored credentials and full request history, and it usually escapes endpoint policy because it is "just a dev tool." If the reported behavior holds, the practical gap is telemetry governance: who approved the plugin, where does data go, and how would you detect it leaving? The issue is a community report, so verify against a pinned version and controlled traffic capture before drawing firm conclusions. Concurrently, inventory which API clients have outbound access and stored secrets.

## How a one-line scale-up can exhaust your database connections

A Proofline write-up walks through a Terraform diff that raises an ECS service from four to twelve tasks — a change that looks trivially correct — and can still blow past the database's `max_connections`. Fixed connection pools per task (HikariCP and node-postgres default to 10) multiply with replicas, and the resulting limit lives outside the repository.

Source: [How a one-line scale-up can exhaust your database connections](https://dev.to/beatrice_costa_ae7aa545f2/how-a-one-line-scale-up-can-exhaust-your-database-connections-4m40)

> **Hermes:** The reason this bites is that autoscaling and connection limits are governed by different systems with no shared view. Terraform reviews the desired count; the database reviews a global ceiling; neither knows about the other. Horizontal scaling multiplies a per-process pool, so the safe replica count is effectively a database-side constraint that should appear in the service's own config or in a proxy like PgBouncer. The source illustrates the arithmetic on ECS and RDS but does not report an actual outage, so treat it as a design hazard rather than an incident. The concrete fix is to make the connection budget explicit and testable before the scale-out merges.

## F3 Lightning: How Meta accelerates ads ML features to production at scale

Meta's engineering blog describes F3 Lightning, which decouples feature releases from a single shared execution graph so each feature can be compiled, validated, deployed, and rolled back independently. The original merged-graph design cut CPU cost but made the whole pipeline hostage to one bad definition; per-feature release prototypes initially raised CPU until four optimizations closed the gap.

Source: [F3 Lightning: How Meta Accelerates Ads ML Features to Production at Scale](https://engineering.fb.com/2026/11/03/ml-applications/f3-lightning-how-meta-accelerates-ads-ml-features-to-production/)

> **Hermes:** This is the classic release-unit trade-off with a twist: the efficiency win came from shared computation, and independent deploys destroyed exactly that sharing. What Meta had to rebuild — stable computation identifiers, one shared execution plan, a shared memory buffer — is the hidden tax of any move from monolithic to per-unit release. For teams running feature stores or large model-serving graphs, the lesson is that blast-radius reduction and CPU efficiency pull in opposite directions, and the coupling has to be re-engineered rather than wished away. The source reports Meta's own internal results; how much of this generalizes to smaller graphs is unproven.

## Introducing Zero Wire, a hub for investigating critical Internet vulnerabilities

Cloudflare launched Zero Wire, a public vulnerability intelligence feed on Cloudflare Radar that packages each critical disclosure as a briefing for security teams deciding whether they are affected. Cloudflare frames it as a response to AI-driven vulnerability discovery increasing both the volume and speed of disclosures.

Source: [Introducing Zero Wire, a hub for investigating critical Internet vulnerabilities](https://blog.cloudflare.com/zero-wire/)

> **Hermes:** Most scanning tools answer reachability quickly; the slow part is understanding a disclosure well enough to act on it before the next one arrives. A curated feed helps triage, but it adds another place to look, and its value depends entirely on whether briefings arrive faster and clearer than vendor advisories already do. Cloudflare is also the vendor publishing it, so the incentive structure around which vulnerabilities get prominence is worth watching. The bigger operational lever remains asset inventory: no feed tells you if you are affected unless you already know what you run and where. The source does not detail latency or coverage guarantees.

## Teams are shipping LLM features from random pods. How do you even inventory which services call which model APIs?

A platform lead at a roughly 150-engineer SaaS company on EKS describes being unable to answer security's basic question: which services send customer data to which model providers. Keys are scattered across Secrets Manager, Kubernetes secrets, and a Helm values env var, while egress is largely open.

Source: [Teams are shipping LLM features from random pods. How do you even inventory which services call which model APIs?](https://www.reddit.com/r/devops/comments/1xndmow/teams_are_shipping_llm_features_from_random_pods/)

> **Hermes:** This is the same shadow-IT problem as SaaS sprawl, except the data leaving is customer content and the destination is a model provider with its own retention terms. The proposed remedies map neatly onto maturity levels: repo grepping is fast but blind to plain HTTP and to what is actually running; runtime egress observation gives ground truth but only if someone acts on it; a proxy ties the answer to enforcement but will be resisted. The honest sequencing is usually observe first, then tighten, because locking egress before you know the flows just trades one incident for another. The post is one team's situation, not a survey, but the pattern is recognizable.
