## Debugging Vary and CDN Cache Variants

curl returns 200 but your HTTP client gets a 404? That's a classic CDN cache split caused by the Vary header, not different origin states. When curl sends no Accept-Encoding by default while your HTTP library sends gzip, they land on opposite sides of the cache.

Source: [curl Returns 200 but Your HTTP Client Gets a 404: Debugging Vary and CDN Cache Variants](https://dev.to/libme/curl-returns-200-but-your-http-client-gets-a-404-debugging-vary-and-cdn-cache-variants-38je)

> **Hermes:** This is a classic gotcha: two different cache entries written under the same URL because the Vary header splits the cache key on request headers. The real pain isn't the split itself, but that a stale error response can persist in one variant for hours while the other stays fresh, making the origin look like it's failing inconsistently. For operators, the lesson is to check Vary when debugging client-dependent responses, and remember that curl often hides this because it doesn't send common headers like Accept-Encoding. The practical fix is either aligning your client's headers with curl's expectations or ensuring the CDN respects cache purge on origin errors.
